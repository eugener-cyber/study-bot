## 0.2 Решения, которые нельзя откатывать

Собрано из истории v3.0 → v3.2. Каждое выглядит произвольным без причины, поэтому причина приводится здесь.

**Mastery считается от стабильности, а не от ретривабилити.** Ретривабилити падает по мере ожидания повторения — это её назначение. Построенная на ней освоенность обваливалась бы сама по себе после любого перерыва, хотя человек не забыл ничего сверх ожидаемого, и роняла бы каскадом адаптивность (§15) и сбор сессии (§16). Стабильность растёт только от реальных успешных повторений.

**Адаптивность задаётся через `desired_retention`, а не множителем интервала.** Это целевая вероятность вспоминания, из которой алгоритм сам выводит интервал. Ручная правка `due_at` разрушает внутреннюю согласованность модели.

**Третья корзина ограничена сутками.** Досрочное повторение даёт малый прирост стабильности и подаёт FSRS искажённый сигнал: потраченное повторение плюс испорченная оценка.

**Дедуп вопросов структурный, а не нечёткий.** Триграммное и токенное сходство плохо работает на перефразировках и даёт ложные срабатывания на структурно похожих, но разных по смыслу вопросах. Уникальный ключ `(fact_id, type, direction)` плюс проверка набора целиком валидатором решают задачу без отдельного механизма.

**Валидатор вопросов обязателен.** Без него 10–20% заданий будут битыми, и доверие к боту исчезнет за неделю. Это не опциональная оптимизация.

**Локальный Bot API server ставится на этапе 1**, даже когда поддерживается только PDF. Публичный Bot API не отдаёт файлы больше 20 МБ; переезд позже меняет способ получения файла во всех адаптерах.

**Состояние повторения висит на факте, а не на вопросе.** Иначе три формулировки одного знания получат три расписания, утроят нагрузку и научат заучивать формулировку.

# 1. Цель, инварианты, границы

## 1.1 Задача продукта

Персональный учебный бот (один-несколько пользователей, не SaaS). Пользователь загружает материал в любом виде — бот строит конспект, банк заданий четырёх типов и **сам возвращает пользователя к материалу по расписанию интервального повторения**, пока знание не закрепится.

Метрика успеха — не число конспектов и не время в боте, а **доля правильных ответов на увеличенных интервалах** (7 и 30 дней, §29).

## 1.2 Критические инварианты

**И-1. Evidence First.** Каждый факт хранит `fragment_ids`, из которых получен; вопрос наследует evidence от факта. Цепочка `question → fact → fragment → locator → исходник` не рвётся нигде.

Ссылка на источник вычисляется программно из `locator`. LLM никогда не называет номер страницы, таймкод или URL самостоятельно — она возвращает только `fragment_ids`, которые проверяются на принадлежность поданному множеству. Вопрос с неразрешимой ссылкой не сохраняется как `valid`.

**И-2. Планируется знание, а не вопрос.** Состояние повторения хранится на `fact`; вопрос выбирается в момент выдачи.

**И-3. Ничто от LLM не попадает в БД без валидации.** Путь: `LLM → schema → business → evidence → БД`. Прямой путь `LLM → БД` запрещён для фактов, конспектов и вопросов.

**И-4. Learning state не меняется без ответа пользователя.** Показ вопроса сам по себе не изменяет FSRS. Состояние меняется только по цепочке `ответ → вердикт → рейтинг → FSRS → review_log`.

**И-5. Abandoned ≠ wrong.** При брошенной сессии FSRS не меняется, `lapses` не растёт, `review_logs` для неотвеченных items не создаётся, факты возвращаются в пул. Единственное, что меняется при показе, — счётчики презентации (`shown_count`, `last_shown_at`, `last_q_type`, `last_direction`): пользователь вопрос всё-таки видел, и повторять ему тот же формат не нужно. Тесты на брошенную сессию должны проверять неизменность FSRS и coverage, а не всей строки `review_states`.

**И-6. Rejected-вопрос не занимает слот генерации.** Он сохраняется для аудита, но не блокирует создание нового вопроса того же `(fact_id, type, direction)`.

**И-7. Fact identity стабильна.** Перегенерация вопросов никогда не создаёт новый `fact_id`. Автоматическая перегенерация фактов после начала обучения запрещена в MVP: состояние FSRS ключом на `fact_id`, и подмена факта молча уничтожает историю. Ошибочный факт переводится в `suspended`, а не заменяется.

**И-8. Старые callback никогда не меняют состояние.** Любой callback проверяет: сессия существует, `status = 'active'`, `session_item.answered_at IS NULL`. При нарушении — `answer_callback_query("Эта сессия уже завершена", show_alert=True)` без изменения БД.

**И-9. Processing stage атомарна.** Каждая стадия либо полностью завершена и отражена в `completed_stages`, либо после сбоя не считается завершённой. Частичные артефакты незавершённой стадии не используются следующей.

**И-10. Внешние знания не являются evidence.** Источник факта — только поданные материалы. Пояснение, которого нет в источнике, помечается `derived = true`.

## 1.3 Границы

Не входит: веб-интерфейс, мобильное приложение, биллинг, совместная работа, геймификация, универсальный краулер.

Доступ — белый список `ALLOWED_USER_IDS`, middleware отклоняет остальных.

| `EmbeddingProvider`, pgvector | Дедуп решён структурно, поиск — средствами Postgres | семантический поиск, этап 3 |
| Лемматизация (pymorphy3) | Привязка к одному языку; `rapidfuzz` решает ту же задачу без зависимости | — |
| Pre-test | Требует готовый банк вопросов, то есть материал уже обработан; FSRS решает «это я знаю» сам | не раньше этапа 3 |
| Celery | ARQ работает в том же asyncio-цикле без второго рантайма | — |
| Собственный алгоритм SRS | FSRS ставится одной командой; «простой сейчас, FSRS потом» стоит полной потери истории | — |
| Автоматическая перегенерация фактов | Меняет смысл learning history (И-7) | отдельный управляемый migration flow |

**Абстракция LLM-провайдера в число отброшенного не входит** (в отличие от v3.1). Выбор провайдера объективно открыт и может смениться — см. §2.1. Остальные три провайдерских интерфейса не нужны: распознавание речи локальное и от выбора не зависит.

Деплой — **четыре контейнера**: `postgres`, `redis`, `telegram-bot-api`, `app` (бот и ARQ-воркер как два процесса одного образа).

## 2.1 LLM-провайдер

**Решено.** Этап 1 — разработка, тестирование и отладка — ведётся на Anthropic Claude API. Промышленная эксплуатация переносится на YandexGPT. Бот предназначен для работы в России, где часть зарубежных провайдеров недоступна по условиям использования, а обход геоограничений означает аккаунт, который может быть закрыт в любой момент; поэтому смена провайдера запланирована заранее, а не является риском.

Это делает абстракцию `LLMProvider` не страховкой, а требованием: у неё с первого дня две реализации, и вторая известна. Любой код, знающий про особенности Anthropic — имена параметров, формат структурированного вывода, счётчики токенов, — живёт только внутри `core/llm/`.

| | Этап 1 (разработка) | Промышленная эксплуатация |
|---|---|---|
| Провайдер | Anthropic Claude API | YandexGPT |
| `LLM_MODEL` | `claude-opus-5` | `TODO(owner)` — по факту доступных моделей |
| `LLM_VISION_MODEL` | `claude-opus-5` (та же модель, vision встроен) | `TODO(owner)` |
| `COST_CURRENCY` | `USD` | `RUB` |
| Стоимость | $5 / $25 за млн токенов (вход / выход) | по тарифам Яндекса |

**Три особенности Anthropic, существенные для архитектуры:**

*Структурированный вывод* задаётся через `output_config.format` на `messages.create()` либо через `messages.parse()` с валидацией по схеме. Параметр `output_format` устарел и в новом коде не используется. Для инструментов строгость схемы включается полем `strict: true` в определении инструмента.

*Механизм цитирования Anthropic использовать нельзя.* У провайдера есть встроенные цитаты с координатами страниц (`page_location`), и соблазн заменить ими `fragment_ids` велик. Он несовместим со структурированным выводом — совместный запрос возвращает 400 — и, что важнее, привязан к одному провайдеру: на YandexGPT его не будет. Схема И-1 остаётся прежней: модель возвращает только `fragment_ids`, программа проверяет их принадлежность поданному множеству (§7.3).

*Пакетная обработка.* Anthropic Batch API выполняет запросы асинхронно за 50% стоимости. Конвейер обработки материала (§4) фоновый, пользователь смотрит на сообщение прогресса, и задержка в несколько минут ничего не меняет. Это делает пакетный режим уместным для стадий `facts` и `questions`, где вызовов больше всего. В MVP не обязателен, но интерфейс `LLMProvider` не должен ему мешать: методы принимают один запрос, а пакетирование, если появится, живёт внутри реализации. На YandexGPT аналога может не быть — поэтому это оптимизация реализации, а не часть контракта.

*Кеширование префикса* оплачивается по сниженному тарифу и применимо к валидатору (§11.4) и судье (§21.3), где факт и тексты фрагментов повторяются между вызовами. Та же оговорка: деталь реализации, не контракт.

```python
class LLMProvider(ABC):
    name: str

    async def structured(
        self, prompt: str, schema: type[BaseModel], *, purpose: str
    ) -> BaseModel: ...

    async def vision(
        self, images: list[ImageInput], prompt: str,
        schema: type[BaseModel], *, purpose: str
    ) -> BaseModel: ...
```

Реализация одна на инсталляцию; маршрутизация между несколькими провайдерами в MVP не делается. Бизнес-логика знает только интерфейс.

Оба метода возвращают не только разобранную модель, но и фактические счётчики токенов и стоимость вызова: без них §6.4 нечем наполнять, а оценка §6.3 не с чем сравнивать. Бизнес-логика этих данных не видит — запись в `llm_calls` выполняет клиент (§6.1).

Учёт стоимости ведётся в валюте провайдера: поле `cost_currency` в `llm_calls`, константа `COST_CURRENCY` в конфиге. Зашитые доллары запрещены — именно потому, что на этапе 1 валюта долларовая, а в эксплуатации рублёвая, и разница обнаружится не при смене провайдера, а в отчётах за месяц.

**Риск перехода на YandexGPT фиксируется здесь, а не обнаруживается потом.** Две возможности не эквивалентны у двух провайдеров: качество структурированного вывода по строгой схеме и наличие vision. Если у YandexGPT vision окажется недостаточным для §5.2 (сканы) и §5.3 (изображения), переход означает не замену класса, а отказ от части источников либо отдельный провайдер только для vision. Проверяется это до перехода, тем же спайком, что и на этапе 1, — а не на работающей системе.

## 3.1 Индексы

```sql
CREATE UNIQUE INDEX ON materials(user_id, (origin->>'sha256')) WHERE origin ? 'sha256';
CREATE INDEX ON materials((origin->>'sha256'));        -- задел под общий кеш обработки
CREATE INDEX ON fragments(material_id, ord);
CREATE INDEX ON review_states(user_id, due_at) WHERE NOT suspended;
CREATE UNIQUE INDEX ON sessions(user_id) WHERE status = 'active';
CREATE INDEX ON questions(fact_id, status);
CREATE INDEX ON questions(fact_id) WHERE status = 'valid';   -- для EXISTS в планировщике
CREATE UNIQUE INDEX ON questions(fact_id, type, direction) WHERE status = 'valid';
```

Последний индекс **обязан быть частичным и ограниченным именно `valid`**. Без условия отклонённая строка занимает слот навсегда: перегенерация падает на `IntegrityError`, и факт теряет этот формат до конца жизни. Это прямое следствие И-6.

Условие `status <> 'rejected'`, стоявшее здесь в v3.4, закрывало только половину проблемы: под него попадали и строки `draft`. Вопрос переходит в `draft` при генерации и в `valid`/`rejected` только после валидации (§11.5), а между этими моментами лежит сетевой вызов. Воркер, упавший в этом промежутке, оставлял `draft` навсегда занимающим слот — то есть воспроизводил ровно ту аварию, ради которой индекс делали частичным. Строки `draft` — частичный артефакт незавершённой стадии `questions` и удаляются при её перезапуске по общему правилу §4.2.

Уникальность по `valid` продолжает защищать от конкурентной регенерации (§18): два воркера могут создать по `draft`, но второй `valid` не закоммитится.

Предпоследний нужен, чтобы условие `EXISTS (... status='valid')` в планировщике (§16) не превращалось в последовательное сканирование.

## 3.2 Шкала важности

```
importance = 3   ключевой факт, без которого тему нельзя считать понятой
importance = 2   существенный
importance = 1   вспомогательный, деталь
```

Шкала фиксирована и используется в трёх местах согласованно: отбор в раздел «Что запомнить» (§8), режимы глубины конспекта (§8), весовой множитель в формуле strength (§14.1). Обратная трактовка взвешивает mastery в пользу тривиальных фактов, поэтому переопределять шкалу нельзя.

## 3.3 Жизненные циклы

**Question:** `draft → valid` либо `draft → rejected`. Rejected не возвращается в ротацию, но освобождает слот `(fact_id, type, direction)` для нового вопроса.

**Fact:** `active → suspended`. Факт не пересоздаётся при перегенерации вопросов (И-7). `suspended = true` означает: не выдавать в SRS, не выбирать вопросы, показывать в конспекте как проблемный, сохранять историю.

**Fact.generation_status:**

```
pending        генерация вопросов ещё не выполнялась
ok             есть валидные вопросы минимум двух типов
single_format  генерация дважды не дала двух разных типов; используется то, что есть (§10.2)
unavailable    исчерпан MAX_REGEN_ATTEMPTS, валидных вопросов нет (§12.1)
```

Планировщик пропускает факты со статусом `unavailable` и факты без валидных вопросов, не меняя при этом их FSRS-состояние.

# 4. Обработка материала

## 4.1 Статусы

```
queued → processing → ready
                   ↘ failed
```

Стадии внутри `processing`, строго по порядку:

```
extract → sections → facts → notes → questions → schedule
```

Последняя стадия обязательна: до неё у фактов нет состояния повторения, и планировщик физически не может их увидеть (§4.6).

Единственная стадия, которую допустимо пропустить, — `questions`, и только при `materials.mode = 'notes_only'` (§6.3). Пропуск фиксируется явно: в `completed_stages` пишется `questions:skipped`, а не `questions`. Разница существенна — по ней возобновление отличает «стадия выполнена» от «стадия сознательно пропущена», а кнопка «Достроить задания» знает, что именно доделывать.

## 4.2 Атомарность стадий

Каждая стадия выполняется в собственной транзакционной границе:

```
BEGIN
  подготовить все артефакты стадии
  проверить артефакты
  удалить предыдущие частичные артефакты этой стадии
  сохранить полный результат
  добавить stage в completed_stages
COMMIT
```

При исключении до COMMIT `completed_stages` не меняется, изменения откатываются, следующая попытка начинает стадию заново.

Файловые артефакты сначала пишутся во временную директорию `.tmp/<material_id>/<stage>/` и переносятся в постоянное хранилище только после успешного коммита. Иначе на диске остаются клипы и картинки от стадии, которая формально не выполнена.

Для стадии `questions` частичным артефактом являются строки `questions` со `status = 'draft'`: вопрос получает окончательный статус только в §11.5, после сетевого вызова валидатора. Перезапуск стадии удаляет все `draft`-строки материала до начала работы. Без этого упавший воркер оставляет за собой занятые слоты генерации (§3.1).

## 4.3 Возобновление

Воркер читает `completed_stages` и начинает с первой незавершённой стадии. Повторный запуск завершённой стадии — no-op. Частичные артефакты незавершённой стадии удаляются перед повторным запуском.

## 4.4 Дубликат материала

Определяется по `sha256` в рамках пользователя. Показывается существующий материал с кнопками `[Открыть]` и `[Перенести в другой предмет]`; второй вариант меняет только `subject_id`, копия не создаётся.

## 4.5 Прогресс и ожидание пользователя

Одно сообщение, редактируемое `edit_message_text` не чаще раза в 5 секунд: `⏳ Распознаю аудио… 4:12 / 58:30`.

Две ситуации требуют ответа пользователя посреди конвейера: подтверждение бюджета (§6.3) и выбор языка при неуверенном определении (§5.4). Обе используют один механизм. Материал остаётся в статусе `processing` с `progress.stage = 'awaiting_user'` и `progress.question`, задача ARQ завершается, а продолжение ставится в очередь обработчиком нажатия кнопки. Фоновый воркер никогда не блокируется в ожидании ответа.

Если ответа нет `AWAITING_USER_TIMEOUT_H` часов, материал переводится в `failed` с понятной причиной; повторная обработка доступна кнопкой.

## 4.6 Стадия schedule

После коммита стадии `questions` для каждого **обучаемого** факта материала (§14.3) создаётся строка `review_states`:

```
due_at        = processed_at + NEW_FACT_DELAY (по умолчанию 10 минут)
stability     = NULL        -- заполнит FSRS при первом ответе
difficulty    = NULL
state         = new
reps = 0, lapses = 0, seen = false
created_at    = now()
introduced_at = NULL        -- проставится при первом ответе, §16.1
```

Вставка идемпотентна (`ON CONFLICT (user_id, fact_id) DO NOTHING`): повторный запуск стадии не сбрасывает уже накопленное состояние. Это прямое следствие И-7 — идентичность факта стабильна, и его расписание не должно обнуляться при переобработке материала.

Факты, не прошедшие фильтр обучаемости (низкая confidence, `derived`, `suspended`, отсутствие валидных вопросов), строку не получают вовсе.

Если факт позже станет обучаемым, строка создаётся отложенно **тем же кодом** — функция `ensure_review_states(fact)` идемпотентна и вызывается из двух мест: из стадии `schedule` по всем фактам материала и из успешного завершения регенерации (§12.2). Второй вызов обязателен и вынесен в критическое свойство №19 (§38): §12.2 обещает, что факт «возвращается в ротацию автоматически», и без явного вызова это обещание не выполняется — факт молча остаётся вне SRS, а увидеть это можно только по отсутствию заданий, которое легко списать на что угодно.

# 5. Адаптеры

## 5.1 Интерфейс

```python
class SourceAdapter(ABC):
    kind: str
    async def probe(self, path: str) -> SourceMeta: ...
    def extract(self, path: str, ctx: IngestCtx) -> AsyncIterator[Fragment]: ...
```

Новый тип источника = адаптер + вариант `Locator`. Больше ничего не меняется.

## 5.2 PDF

1. PyMuPDF постранично: `page.get_text("dict")`.
2. Детект скана: менее 100 символов текста при непустом изображении → страница рендерится в PNG 150 dpi и уходит в vision. Tesseract не использовать.
3. Текстовые блоки склеиваются во фрагменты 600–900 токенов по границам абзацев; `bbox` фрагмента = объединение bbox его блоков. **Фрагмент не пересекает границу страницы**: `locator` (§3.4) хранит ровно один номер страницы, и склейка через разворот дала бы ссылку на источник, указывающую не туда. На разреженном материале это означает фрагменты меньше 600 токенов — верхняя граница обязательна, нижняя нет.
4. Изображения площадью больше `MIN_IMAGE_AREA_RATIO` страницы → `media_assets` + фрагмент `kind='image'` + описание vision. Они же дают материал для `match_image`.

   **Порог сам по себе недостаточен, нужно правило группы.** Фиксированные 4% написаны в расчёте на учебник с крупными иллюстрациями. На олимпиадном материале профиля «Культура дома, дизайн и технологии» картинки мелкие и осмысленны только наборами: замеры на реальном задании регионального этапа дали 20 изображений, из которых порог прошли 8. Отброшенными оказались ровно те, ради которых существует `match_image` — страница «Рис. 1. Виды графических элементов для выполнения задания» с десятью пронумерованными элементами, из которых восемь укладываются в 2.9–4.2%, и группа из четырёх связанных изображений на другой странице с долями 2.8–3.7%.

   Поэтому: изображения одной страницы, образующие пронумерованный набор при подписи вида «Рис. N», сохраняются **целиком, независимо от площади каждого**, и получают общий `group_id` в `locator`. Единица, которую потребляет `match_image`, — набор, а не отдельная картинка; разорванный набор бесполезен и при этом неотличим от отсутствия материала.
5. Заголовки: `doc.get_toc()`; при отсутствии — эвристика по кеглю выше медианного. На проверенном материале оглавления нет, то есть **штатным путём является эвристика, а не исключение** — и тестами покрывается она.
6. `fragments.quality`: `1.0` для текстового слоя, собственная `confidence` vision для распознанного содержимого. Фиксированных констант здесь нет.

## 5.3 Изображения

JPG/PNG/WEBP → vision, ресайз по длинной стороне до 1568 px:

```json
{"description":"…","ocr_text":"…","kind":"scheme|table|chart|photo|text",
 "elements":[{"label":"…","region":[x0,y0,x1,y1]}],"confidence":0.0}
```

`elements.region` используется как evidence locator.

## 5.4 Аудио

`faster-whisper`, сегменты объединяются во фрагменты 500–800 токенов, `locator.start/end` по крайним словам. При уверенности определения языка ниже `LANG_CONFIDENCE_MIN` язык выбирает пользователь кнопками.

## 5.5 Видео

Параллельно: `ffmpeg -vn -ac 1 -ar 16000` → аудио → §5.4; PySceneDetect (`ContentDetector`, threshold ≈ 27) → кадры сцен → vision.

Не более `MAX_SCENES` сцен на материал; при превышении берутся сцены с максимальным изменением кадра, иначе стоимость vision растёт неограниченно.

Слайд и попадающие в его интервал фрагменты транскрипта получают общий `scene_id` в `locator` и передаются модели совместно: «что говорят» плюс «что показывают».

## 5.6 Сайт

Анализ конкретного сайта выполнен. Заказчик назвал источником `postupi.online`, раздел ВсОШ по труду (технологии), профиль «Культура дома, дизайн и технологии», 9–11 класс, задания всех этапов и теория.

### Что прямо запрещено правилами самого сайта

Пользовательское соглашение, п. 2.4.2 — «При использовании Сайта Пользователю запрещается: … **копировать и использовать информацию с Сайта** … (как полностью, так и отдельные элементы); **перерабатывать или изменять текстовую или графическую информацию**».

Правила цитирования — «**Полное копирование материалов разрешено только с письменного согласия редакции.**»

Конвейер §4 делает буквально оба названных действия: копирует текст во `fragments` и перерабатывает его в факты, конспект и банк заданий. Запрет адресован пользователю, поэтому **наличие действующей учётной записи его не снимает, а распространяет на владельца записи**.

Отдельно: правила сайта оговаривают, что за материалами, права на которые принадлежат третьим лицам, следует обращаться к правообладателям напрямую. Задания ВсОШ подготовлены ЦПМК и Минпросвещения, а не редакцией портала, — то есть портал и сам не является правообладателем нужного нам содержания.

### Вывод

Сайт **непригоден как источник для автоматического сбора**, и причина не техническая. `robots.txt` при этом запрещает ровно то, что нужно для `match_image` (§9.1), то есть даже частичный сбор дал бы материал без изображений.

Это тот самый случай, ради которого §5.6 требовал анализа **до** написания импортёра: импортёр был бы написан и выброшен.

### Рекомендуемая замена источника

Предметная область сохраняется полностью; меняется носитель. Задания ВсОШ и методические рекомендации ЦПМК по профилю «Культура дома, дизайн и технологии» публикуются первоисточниками в виде свободно скачиваемых PDF — организаторами олимпиады и региональными площадками. Такой материал:

- обрабатывается **существующим** PDF-адаптером (§5.2), то есть этапом 1, без единой строки веб-импортёра;
- даёт более качественный evidence: подсветка конкретной страницы первоисточника вместо цитаты с сайта-агрегатора;
- не создаёт правовой проблемы: документы опубликованы для свободного доступа.

**Комплектность источника обязательна, и это не организационное пожелание.** Сухой прогон на реальном задании регионального этапа показал: лист заданий без ключа ответов даёт 41% фактов со статусом `derived`, то есть выше порога `DERIVED_WARN_RATIO`. Причина в устройстве материала. Часть вопросов содержит знание в самой формулировке, а ответом служит термин («изделие из трёх простёганных слоёв…» — что это?) — такой факт подтверждён источником. Другая часть даёт вопрос и варианты, не называя верного; чтобы получить факт, нужно знание извне, а по И-10 внешнее знание evidence не является. По §7.3, проверка 4, такие факты в обучении не участвуют, и до трети материала оказывается непроверяемым.

Поэтому единицей загрузки считается **комплект за один год и класс: задания + ответы с критериями оценивания + теоретические материалы профиля**. Методические рекомендации ЦПМК содержат всё три. На том же материале комплект снижает долю `derived` примерно до 10% и делает генерируемым `match_image`, которому иначе неоткуда взять эталон.

Отдельно: лист заданий — материал проверочный, а не учебный. Он показывает, что спросят, но не объясняет предмет. Обучение только на заданиях даёт заучивание формулировок вопросов — ровно то, против чего направлено правило §10.1.

Веб-импортёр при этом остаётся на этапе 3 как в v3.4 — для источников, которые появятся позже.

**Решено заказчиком:** источником служат опубликованные PDF первоисточников — требования и задания ЦПМК, материалы региональных организаторов. `postupi.online` как источник не используется. Единственный законный путь к нему — письменное согласие редакции; для олимпиадных заданий это обход ради материала, который у первоисточника открыт, поэтому в план он не ставится.

### Базовый вариант импортёра, когда он понадобится

httpx + trafilatura, фрагменты по абзацам, `locator.quote` — первые ~60 символов точной фразы.

# 6. LLM layer

## 6.1 Общие правила

Структурированный вывод — через механизм structured output провайдера со строгой схемой; парсинг свободного текста только как запасной путь.

Ретраи: 429 и 5xx — экспоненциальный backoff, до 4 попыток; ошибка схемы — один повтор с приклеенным текстом ошибки, затем `failed`. Параллелизм ограничен `LLM_CONCURRENCY`.

Каждый вызов пишется в `llm_calls` с `prompt_version` и `provider`. Промпты лежат в `core/llm/prompts/*_v1.md`, версия в имени файла обязательна: это позволяет понять, какие объекты созданы устаревшим промптом, и перегенерировать точечно.

## 6.2 Размер контекста

`MAX_SECTION_TOKENS` — обязательная константа. Один вызов на секцию допустим, только если секция в неё помещается. Иначе:

```
section → semantic chunks → facts per chunk → merge → dedup
```

Без этого ограничения документ без оглавления, где заголовки определяются эвристикой, способен дать «секцию» на пятьдесят страниц.

## 6.3 Бюджет

**Оценка считается до стадии `extract`, а не после неё.** В v3.4 гейт стоял после `extract`, и для сканированного PDF это означало следующее: `extract` — это vision-вызов на каждую страницу (§5.2), то есть основная статья расхода по материалу, и пользователя спрашивали «обрабатывать?» после того, как деньги уже потрачены. На трёхсотстраничном скане такой гейт бессмыслен.

Оценка строится в два приёма:

```
probe    -> pages | duration | размер текста          -> предварительная оценка, гейт
extract  -> fragments × average_size × coefficients   -> уточнённая оценка
```

Предварительная оценка получается из `SourceAdapter.probe` (§5.1) — числа страниц и доли страниц, требующих vision, либо длительности дорожки — умноженных на коэффициенты стадий. Она сохраняется в `materials.cost_estimate` вместе с валютой и **служит основанием гейта**. После `extract` оценка пересчитывается по фактическому числу фрагментов и перезаписывается там же; именно уточнённая оценка сравнивается с фактом в §6.4.

Если предварительная оценка превышает `COST_WARN_THRESHOLD`, обработка **не начинается** до выбора пользователя (механизм ожидания — §4.5):

```
Материал большой: ~180 страниц, примерно N токенов, ≈ X <валюта>.
[Обработать полностью]  [Только конспект, без тестов]  [Отмена]
```

Если уточнённая оценка после `extract` превышает предварительную более чем в `COST_REESTIMATE_FACTOR` раз, пользователь спрашивается повторно тем же механизмом. Без этой проверки гейт обходится любым материалом, чью стоимость `probe` недооценил.

Прерывание на середине недопустимо: половинчатый материал имеет факты без вопросов и конспект без части разделов, и пользователь не может понять, что у него на руках.

### Режим «Только конспект, без тестов»

Выбор этой кнопки — не отмена и не сбой, а отдельное состояние материала, и оно должно быть различимо:

```
materials.mode = 'notes_only'
completed_stages: [..., 'notes', 'questions:skipped', 'schedule']
```

Стадия `questions` не выполняется. Стадия `schedule` выполняется и не создаёт ни одной строки `review_states`: у фактов нет валидных вопросов, значит они не обучаемы (§14.3). Материал получает статус `ready`.

Последствия для пользователя обязаны быть видимыми, а не выводимыми: в карточке материала и в §29 такой материал показывается как «конспект без заданий», секции дают «нет заданий» вместо mastery (§14.1), и присутствует кнопка **«Достроить задания»**. Нажатие ставит материал обратно в `processing`, переводит `mode` в `full` и запускает конвейер со стадии `questions` — то есть обычное возобновление по §4.3, для которого `questions:skipped` и отличается от `questions`.

Критерий §6.4 к материалам в режиме `notes_only` не применяется: сравнивать полную оценку с расходом на усечённом конвейере бессмысленно.

## 6.4 Учёт стоимости

Для каждого вызова хранятся `provider`, `model`, `pricing_version`, токены, `cost_currency`, `estimated_cost`, `actual_cost`. Критерий приёмки: `abs(actual − estimate) / estimate ≤ 0.4` на материалах, где оценка достаточно велика для осмысленного сравнения.

# 7. Knowledge layer

## 7.1 Извлечение фактов

Фрагменты группируются в секции (оглавление, смысловые сдвиги транскрипта, сцены). Один вызов на секцию или чанк:

```json
{
  "title": "string",
  "summary_md": "3-8 предложений",
  "facts": [{
    "statement": "проверяемое утверждение одним предложением",
    "detail": "1-2 предложения раскрытия",
    "kind": "definition|cause|difference|property|formula|example",
    "fragment_ids": [12, 13],
    "importance": 3,
    "difficulty": 2,
    "derived": false,
    "confidence": 0.9
  }]
}
```

В промпте шкала важности приводится явно: **3 — ключевой факт, 2 — существенный, 1 — вспомогательный** (§3.2).

## 7.2 Правила факта

`statement` — одно проверяемое утверждение, одно предложение, без внешнего знания. `detail` — 1–2 предложения, попадают в разбор ответа. `derived = true` — утверждение не сказано напрямую, а выведено моделью. `confidence` снижается при неоднозначности, обрыве фразы, плохом распознавании.

## 7.3 Evidence validation

**Проверка 1.** `fact.fragment_ids ⊆ submitted_fragment_ids`. Нарушение — факт отбрасывается. Это защита И-1: без неё вся цепочка ссылок фиктивна, потому что модель выдумает идентификаторы.

**Проверка 2.** `final_confidence = confidence × min(fragment.quality)`.

**Проверка 3.** `final_confidence < MIN_FACT_CONFIDENCE` — факт сохраняется, показывается в конспекте с пометкой `⚠️`, вопросы по нему не генерируются.

**Проверка 4.** `derived = true` — факт сохраняется в конспекте с маркировкой и **не участвует в SRS** в MVP: обучение строится только на непосредственно подтверждённых утверждениях.

**Наблюдаемость проверки 4.** Решение о `derived` принимает модель. Если она окажется осторожной, значительная часть знания молча выпадет из обучения, а пользователь увидит лишь, что вопросов подозрительно мало. Поэтому доля `derived` считается по материалу, и при превышении `DERIVED_WARN_RATIO` пользователь получает сообщение: «N% фактов помечены как выводы модели и не попадут в тесты — проверьте конспект».

## 7.4 Дедуп фактов

Первичный признак — `norm_hash`: NFKC-нормализация, lowercase, удаление пунктуации, схлопывание пробелов. Кандидаты дополнительно сравниваются `rapidfuzz.token_set_ratio > FACT_DEDUP_THRESHOLD`.

При конфликте сохраняется версия, более богатая evidence; при равенстве — с большей confidence; затем с большей importance.

Автоматическое объединение уже обучаемых фактов запрещено (И-7).

# 8. Конспект

Конспект строится **из сохранённых фактов**, а не из сырого текста.

```
## Название темы
{section.summary_md}

### Ключевые понятия
— термин — определение

### Основные положения
— факт   (⚠️ у derived и у низкой confidence)

### Связи и отличия

### Что запомнить
— факты с importance = 3
```

Три режима глубины — фильтрация уже сохранённых фактов, а не дополнительные вызовы модели, поэтому переключение мгновенное и бесплатное:

```
краткий     importance = 3
средний     importance = 2..3
подробный   все факты
```

`summary_md` секции показывается во всех режимах.

## 8.1 Выдача

Навигация: секция → страница → следующая/предыдущая. Кнопка `📥 Скачать` отдаёт `.md` и `.pdf`.

Лимит Telegram в 4096 символов применяется **к отрендеренному HTML после экранирования**, а не к исходному Markdown: экранирование расширяет текст (`&` → `&amp;`), теги добавляют байты, и пагинатор, считающий по сырому источнику, регулярно выдаёт сообщения сверх лимита. Пагинатор обязан гарантировать длину фактически отправляемого сообщения.

# 9. Банк вопросов

## 9.1 Типы

MVP: `mcq`, `open`, `match_text`, `match_image` — дискриминированный union по `type`. Без изменения модели позже добавляются `cloze`, `ordering`, `true_false`.

## 9.2 Payload

```jsonc
// mcq
payload: {"question":"…","options":["A","B","C","D"]}
answer:  {"correct_index":2}

// open
payload: {"question":"…","hint":"…|null"}
answer:  {"reference":"эталон","accept":["синоним","альт. формулировка"],
          "must_include":["ключ1","ключ2"]}   // подсказка судье, не автовердикт

// match_text — 3..5 пар
payload: {"prompt":"Соотнесите термин и определение",
          "left":["Митоз","Мейоз","Амитоз"],
          "right":["редукционное деление","деление без веретена","…"]}
answer:  {"pairs":[[0,2],[1,0],[2,1]]}

// match_image — 2..4 пары
payload: {"prompt":"…","left":["Подпись 1","Подпись 2"],"asset_ids":[17,18]}
answer:  {"pairs":[[0,1],[1,0]]}
```

Ограничения платформы: вариантов mcq не более 4; текстовое соотнесение 3–5 пар, картиночное 2–4; текст кнопки до 64 символов, поэтому длинные варианты нумеруются в теле сообщения, а на кнопках остаются цифры; `callback_data` до 64 байт.

# 10. Генерация вопросов

## 10.1 Один вызов на факт

Все вопросы одного факта генерируются одним вызовом: 2–4 вопроса, минимум двух разных типов, пары `(type, direction)` внутри набора уникальны.

```
forward:  термин → определение
reverse:  определение → термин
```

Один вызов вместо нескольких даёт две вещи: набор гарантированно разнообразен по построению, и семантический дедуп выполняется валидатором, которому набор виден целиком (§11.3). Отдельный механизм нечёткого сравнения не нужен.

**Правила промпта.** Вопрос проверяет понимание, а не узнавание формулировки — дословный `statement` с дыркой отбраковывается. Дистракторы из той же предметной области, сопоставимой длины и грамматической формы, правдоподобные, но однозначно неверные по источнику. «Все перечисленное» и «ничего из перечисленного» запрещены. Ответ следует только из поданных фрагментов. Язык вопроса — язык источника. Отдельное объяснение не генерируется: в разборе используется `facts.detail`, что экономит вызов и гарантирует согласованность разбора с конспектом.

## 10.2 Проверка структуры набора

Здесь проверяется только то, что относится к набору **как целому**, потому что отказ на этом уровне ведёт к перегенерации всего набора. Проверки отдельного вопроса лежат в §11 и приводят к отклонению одного вопроса, а не всех.

1. 2–4 вопроса;
2. минимум два разных типа;
3. `(type, direction)` уникальны внутри набора;
4. `match_image` присутствует только при наличии подходящих `media_assets`.

Нарушение — одна повторная генерация. После второй неудачи `facts.generation_status = 'single_format'`, и валидные вопросы, которые всё же получились, используются как есть.

Требования «вопрос проверяет понимание, а не копирует `statement`» и «ответ выводится только из evidence» **не проверяются программно**: они закладываются в промпт (§10.1) и проверяются валидатором (§11.4). Попытка выразить их кодом даёт либо тривиальную проверку на точное совпадение строк, либо эвристику, которая отбраковывает корректные вопросы.

## 10.3 Две разные сложности

`fact.difficulty` — сложность **знания**, используется в аналитике и оценке материала. `question.difficulty` — сложность **задания**. В отборе вопроса (§13.3) участвует только `question.difficulty`. Смешивать их нельзя: простое знание допускает трудное задание и наоборот.

# 11. Валидация вопросов

Проверяется **каждый вопрос по отдельности**; невалидный отклоняется, остальные вопросы набора сохраняются. Порядок: `schema → лексика → evidence → LLM validator`. Программные проверки идут первыми, потому что бесплатны и отсеивают большинство брака.

## 11.1 Schema и формальные ограничения

Поля заполнены; `correct_index` в границах массива; пары образуют биекцию; в `left`/`right` нет дублей; число вариантов и пар в пределах §9.2.

Дополнительно — длина: правильный вариант не превышает медиану дистракторов более чем в `LENGTH_LEAK_FACTOR` раз. Заметно более длинный правильный ответ выдаёт себя без знания предмета.

Запрещённые формулировки («все перечисленное», «ничего из перечисленного») отклоняют вопрос, а не набор.

## 11.2 Lexical leakage

Детерминированная нормализация: NFKC → lowercase → удаление пунктуации → токенизация по буквам и цифрам Unicode → удаление стоп-слов → схлопывание повторов.

```
overlap(correct, question) <= max(overlap(distractor_i, question)) + LEXICAL_LEAK_MARGIN
```

Смысл проверки: если правильный вариант делит с телом вопроса заметно больше содержательных слов, чем любой дистрактор, ответ угадывается без знания предмета.

Исключения (числа, формулы, общеупотребительные термины, короткие служебные слова) фиксируются юнит-тестами, а не описываются прозой.

## 11.3 Evidence

`fact.fragment_ids` непусто, все фрагменты существуют, каждый `locator` разрешается в ссылку.

## 11.4 LLM validator

Один вызов на весь набор вопросов факта. Вход: факт, фрагменты, все вопросы.

```json
{"questions":[{"idx":0,"valid":true,"single_answer":true,
               "grounded":true,"ambiguous":false,"reason":null}],
 "near_duplicates":[[0,2]]}
```

Проверяется: ровно один правильный ответ; дистракторы действительно неверны по фрагменту; ответ следует из evidence; нет двусмысленности; нет смысловых дублей внутри набора.

## 11.5 Сохранение

Валидные → `status='valid'`. Невалидные → `status='rejected'` с `reject_reason`. Из пары семантических дублей остаётся тот, чей тип реже представлен среди валидных вопросов факта.

По завершении валидации выставляется `facts.generation_status`: `ok`, если есть валидные вопросы минимум двух типов, иначе `single_format`.

# 12. Регенерация

Запускается после жалобы пользователя, после отклонения валидатором или по явной внутренней задаче. В промпт передаются текст жалобы, отклонённый вопрос, факт и evidence. Новый вопрос получает `generation_attempt = previous_max + 1`.

## 12.1 Ограничение

Для одного `(fact, type, direction)` допускается не более `MAX_REGEN_ATTEMPTS` попыток.

Отдельного поля под «недоступный слот» не заводится: состояние выводится из уже имеющихся данных — `max(generation_attempt)` по строкам этого слота достиг предела, а строки со `status='valid'` нет. Отклонённые вопросы сохраняются (И-6), поэтому история попыток всегда доступна.

Если валидных вопросов не осталось у факта целиком, выставляется `facts.generation_status = 'unavailable'`.

Ограничение обязательно: факт с объективно неоднозначным источником иначе крутится в цикле «сгенерировать — отклонить» бесконечно, расходуя бюджет.

## 12.2 Факт без валидных вопросов

Факт остаётся в расписании, но планировщик его не выдаёт (§16), FSRS не меняется. В статистике отражается как «не удалось подготовить задание».

Как только регенерация создаёт валидный вопрос, факт возвращается в ротацию автоматически. «Автоматически» здесь означает конкретное действие, а не самопроизвольное следствие: **последним шагом успешной регенерации вызывается `ensure_review_states(fact)`** (§4.6), и `facts.generation_status` пересчитывается с `unavailable` на `ok` или `single_format`.

Оба действия обязательны и в v3.4 отсутствовали. Факт, ставший обучаемым после регенерации, может вовсе не иметь строки `review_states` — если на момент стадии `schedule` валидных вопросов у него не было, строка не создавалась (§4.6). Без явного вызова такой факт остаётся вне SRS навсегда, при этом он числится обучаемым в знаменателе coverage (§14.3) и тем самым занижает mastery. Симптом — «заданий по теме подозрительно мало» — не указывает на причину, поэтому поведение вынесено в критическое свойство №19 (§38).

# 13. Педагогический слой

## 13.1 FSRS

`py-fsrs`, состояние на `(user_id, fact_id)`. `review_logs` пишется на каждый ответ полностью — это то, что делает возможным пересчёт при смене алгоритма или параметров, поэтому поля `fsrs_version` и `planner_version` обязательны.

Первое предъявление: при `reps = 0` неверный ответ даёт `Again`, но `lapses` не увеличивается — человек только впервые встретил факт, это не забывание.

**Предельный интервал.** `Scheduler` создаётся с `maximum_interval = MAX_INTERVAL_DAYS` (§30.3). Без потолка длинная серия верных ответов уводит факт на годы: при `desired_retention` 0.87 восьмое повторение приходится на 12180-й день. Такое расписание — молчаливое исключение факта из ротации, которого не видно ни в mastery, ни в покрытии банка.

Внутри горизонта подготовки потолок почти ничего не меняет: в окне 120 дней при `desired_retention` 0.90 факт получает четыре повторения и с ним, и без него. Цена — порядка двух лишних выдач на факт в год. Это страховка от ошибки модели, а не механизм ускорения.

**Параметры FSRS остаются стандартными.** Алгоритм поставляется с коэффициентами, подогнанными на чужой популяции, и предполагает переподгонку на данных конкретного пользователя примерно после тысячи ответов. Подгонка **сознательно отнесена к этапу 3** (§34): до неё нужны накопленные `review_logs`, которых в первые месяцы эксплуатации не существует. Полнота журнала (см. выше) — именно то, что делает эту отложенную работу возможной.

## 13.2 Соответствие результата рейтингу

| Ситуация | Rating |
|---|---|
| неверно / «не знаю» / пропуск | Again (1) |
| частично верно | Hard (2) |
| верно, но дольше `SLOW_MS` | Hard (2) |
| верно | Good (3) |
| верно, быстрее `FAST_MS`, и `reps > 2` | Easy (4) |

Для соотнесений: менее половины пар — `Again`, от половины — `Hard`, полное совпадение — по общему правилу.

## 13.3 Выбор вопроса

```
1. status='valid' AND type≠last_q_type AND direction≠last_direction AND difficulty≤cap
2. то же без условия на direction
3. то же без условия на type
4. то же без условия на difficulty
ORDER BY shown_count ASC, last_shown_at ASC NULLS FIRST
LIMIT 1
```

Последний шаг обязателен. У факта с двумя вопросами одного типа условие `type ≠ last_q_type` не выполнится никогда, и без отката факт выпал бы из повторений навсегда.

**Порядок шагов 3 и 4 изменён относительно v3.4**, где ограничение по сложности снималось раньше ограничения по типу. Тот порядок противоречил приёмке §34 («вопрос со сложностью выше cap не выбирается, если подходящий существует»): факт, у которого альтернативный по типу вопрос сложнее cap, а подходящий по сложности вопрос того же типа существует, получал вопрос сверх cap. Потолок сложности — часть адаптивности (§15) и защищает пользователя со слабым освоением темы от заведомо непосильного задания; разнообразие типов — оптимизация против заучивания формулировки. При конфликте приоритет у потолка.

После выдачи обновляются `last_q_type`, `last_direction`, `shown_count`, `last_shown_at`. Это счётчики презентации, а не learning state, поэтому И-4 они не нарушают.

# 14. Mastery

Считается на уровне секции, на лету, без кеширующей таблицы.

## 14.1 Формула

```
S_i        = стабильность факта i в днях (FSRS)
base_i     = min(1, ln(1 + S_i) / ln(1 + MASTERY_HORIZON_DAYS))
penalty_i  = 1 − 0.15 × min(lapses_i, 3) / 3
score_i    = base_i × penalty_i,   при reps_i < 2:  score_i ≤ 0.5

strength   = Σ(importance_i × score_i) / Σ importance_i      по seen-фактам
coverage   = seen_facts / teachable_facts
mastery    = coverage × strength

если seen_facts = 0:      strength = 0, mastery = 0
если teachable_facts = 0: секция не имеет mastery, показывается как «нет заданий»
```

Оба вырожденных случая обязательны к явной обработке: `Σ importance` по пустому множеству равна нулю, и формула без этой оговорки даёт деление 0/0 на каждой новой секции — то есть на всём материале сразу после обработки.

Весовой множитель `importance` корректен только при шкале «3 = максимальная важность» (§3.2).

**Почему стабильность, а не ретривабилити.** См. §0.2: ретривабилити падает по мере ожидания повторения по определению, и mastery на ней обваливалась бы от одного лишь течения времени.

**Почему множитель coverage.** Пока большая часть фактов темы не пройдена, mastery структурно не может быть высокой. Один идеальный ответ не означает освоения темы.

## 14.2 Определение seen

Факт считается `seen`, если ему был показан вопрос **и** пользователь отправил ответ либо явное «Не знаю». Флаг хранится в `review_states.seen`. В тот же момент и в той же транзакции проставляется `introduced_at` (§16.1), если он ещё пуст.

Если сессия брошена до ответа — `seen` не выставляется и coverage не меняется. Иначе открывая и бросая сессии можно было бы накручивать mastery без единого ответа.

## 14.3 Обучаемые факты

Факт **обучаем** (`teachable`), если выполнено всё:

```
NOT suspended
NOT derived
final_confidence >= MIN_FACT_CONFIDENCE
generation_status <> 'unavailable'
EXISTS валидный вопрос
```

Это единое определение используется в трёх местах: знаменатель coverage (§14.1), фильтр планировщика (§16), создание строк `review_states` (§4.6). Реализуется одним SQL-предикатом или view, а не тремя похожими условиями в разных модулях — расхождение между ними даёт факты, которые числятся в статистике, но никогда не выдаются, либо наоборот.

В v3.3 четыре по сути одинаковых случая (низкая confidence, `derived`, `suspended`, `unavailable`) трактовались по-разному: три исключались, один — нет.

**Видимая цена исключения.** Убирая необучаемые факты из знаменателя, мы получаем честную оценку по тому, что система в состоянии проверить, но рискуем показать 100% mastery на двадцати фактах из двухсот. Поэтому рядом с mastery в §29 всегда показывается покрытие банка:

```
Гликолиз  ███████░░░ 72%     задания есть для 34 из 41 факта
```

Без этой второй цифры первая вводит в заблуждение, а причина остаётся невидимой.

**Знаменатель подвижен, и это принято сознательно.** Обучаемость зависит в том числе от наличия валидного вопроса, а вопрос можно потерять уже после начала обучения: жалоба пользователя переводит его в `rejected` (§24.2), а регенерация может не дать замены. Если это был последний валидный вопрос факта, факт выпадает из знаменателя coverage, и mastery секции **вырастет** — при том, что пользователь не ответил ни на один новый вопрос.

Альтернатива — заморозить знаменатель на момент обработки материала — хуже: она возвращает ту самую неоднородность, ради устранения которой в v3.4 вводилось единое понятие `teachable`, и оставляет в знаменателе факты, которые система заведомо не в состоянии проверить. Критическое свойство №9 (§38) запрещает изменение mastery от одного лишь течения времени и этот случай не покрывает: здесь изменение вызвано действием пользователя.

Поэтому поведение допустимо, но обязано быть объяснимым: вторая цифра «задания есть для 34 из 41 факта» меняется одновременно с процентом, и по ней видно, что изменился знаменатель, а не знание.

## 14.4 Freshness

```
freshness = среднее R_i по фактам секции
```

Показывается отдельно, как «требует освежения», и **ни на что не влияет**: расписанием занимается FSRS, а адаптивность гейтится по mastery.

## 14.5 Слабая тема

```
strength < WEAK_STRENGTH  AND  coverage > WEAK_MIN_COVERAGE
```

# 15. Адаптивность

| mastery | cap по question.difficulty | desired_retention |
|---|---:|---:|
| < 0.4 | 1 | 0.93 |
| 0.4–0.75 | 2 | 0.90 |
| > 0.75 | 3 | 0.87 |

`desired_retention` передаётся в конфигурацию планировщика FSRS напрямую. Ручные множители на `due_at` запрещены: это целевая вероятность вспоминания, из которой алгоритм сам выводит интервал, а правка результата ломает согласованность модели.

# 16. Сбор сессии

Кандидаты отбираются одним запросом с общим фильтром пригодности:

```sql
FROM review_states rs
JOIN facts f ON f.id = rs.fact_id
WHERE rs.user_id = :uid
  AND NOT rs.suspended
  AND <predicate teachable(f)>          -- §14.3, один и тот же предикат везде
```

Условие `EXISTS` обязано находиться в запросе, а не в коде после выборки: иначе на материале с большим числом непригодных фактов планировщик перебирает их на каждом тике.

Mastery секций вычисляется **один раз на сборку сессии** и переиспользуется для корзины 3 и для cap по сложности (§15). Внутри цикла по кандидатам её пересчитывать нельзя.

Четыре корзины, добираются сверху вниз до `session_size`:

1. **Просроченные** более чем на `OVERDUE_DAYS`.
2. **Обычные due** (`due_at <= now()`), сортировка `lapses DESC, due_at ASC` — факты, на которых человек регулярно ошибается, идут первыми.
3. **Слабые темы** с `due_at <= now() + 24h`, только для добора. Досрочные повторения за пределами суток запрещены (§0.2).
4. **Новые факты**, не более остатка `new_per_day` на текущие локальные сутки (§16.1); первый срок — `processed_at + NEW_FACT_DELAY` (§4.6), порядок между материалами по `materials.created_at`, внутри материала по `importance DESC`.

**Interleaving:** не более 2 подряд одного типа, не более 2 подряд из одной секции, при наличии due-фактов из разных предметов — чередовать. Перемешивание не украшение: последовательный проход одной темы создаёт иллюзию усвоения.

Если ограничения невозможно выполнить из-за малого числа кандидатов, приоритет у корректности отбора по сроку, а не у искусственного заполнения сессии.

Если после всех правил кандидатов меньше `MIN_SESSION_ITEMS`, сессия не создаётся и факты ждут следующего тика.

## 16.1 Подсчёт `new_per_day`

`new_per_day` ограничивает число **новых фактов, реально введённых в обучение** за локальные сутки пользователя:

```sql
SELECT count(*) FROM review_states
WHERE user_id = :uid
  AND introduced_at >= <начало локальных суток пользователя>
```

`introduced_at` проставляется ровно один раз — в тот же момент, когда `seen` переводится в `true` (§14.2), то есть при первом полученном ответе на факт, включая явное «Не знаю». До этого момента поле остаётся `NULL`.

Такое определение выбрано по тем же причинам, по которым `daily_cap` считается по отвеченным заданиям (§17): ограничивается реальная учебная нагрузка, а не число отправленных сообщений. Три альтернативы отвергнуты явно, потому что каждая выглядит правдоподобно и агент выбрал бы любую:

| Трактовка | Почему отвергнута |
|---|---|
| Число фактов, **показанных** сегодня впервые | Брошенная сессия съедала бы дневную норму новизны, нарушая И-5 |
| Число строк `review_states`, **созданных** сегодня | Считает обработку материала, а не обучение: загрузка учебника мгновенно исчерпывает лимит на много дней вперёд |
| Число фактов в состоянии `new` с наступившим `due_at` | Не счётчик, а размер очереди: не убывает от занятий и потому ничего не ограничивает |

В сессию попадает не более `new_per_day − <уже введено сегодня>` новых фактов. Если остаток равен нулю, корзина 4 пуста, и сессия собирается из первых трёх корзин или не собирается вовсе.

# 17. Scheduler

ARQ cron раз в минуту:

1. найти пользователей вне тихих часов, с `paused = false` и наличием `due_at <= now()`;
2. проверить `daily_cap` и отсутствие активной сессии. `daily_cap` считается как число `session_items` с непустым `answered_at` за текущие **локальные сутки пользователя**: ограничивается реальная нагрузка, а не число отправленных сообщений, иначе брошенная сессия съедала бы дневной лимит. Остаток `new_per_day` считается отдельно и по тому же принципу (§16.1), но лимитирует только корзину 4 и никогда не блокирует сессию целиком: повторения должны идти и после исчерпания дневной нормы новизны;
3. проверить `MIN_PUSH_INTERVAL`;
4. собрать сессию (§16) и отправить первое задание.

Отдельная задача в очереди на каждую карточку не создаётся — только выборка по индексу `(user_id, due_at)`.

## 17.1 Тихие часы

Интервал 23:00–08:00 имеет `quiet_from > quiet_to`, и наивное сравнение даёт круглосуточную тишину:

```python
def in_quiet(t, qf, qt):
    if qf > qt:
        return qf <= t or t < qt
    return qf <= t < qt
```

Тестируются: интервал через полночь, интервал внутри дня, границы, равные значения.

## 17.2 Брошенная сессия

Через `ABANDON_AFTER_HOURS` без ответа — `status = 'abandoned'`. FSRS не меняется, факты возвращаются в пул (И-5).

## 17.3 Лимиты Telegram

Ориентироваться на фактические `RetryAfter` и уважать `retry_after`. Ограничение примерно одно сообщение в секунду на чат учитывается троттлером.

# 18. Гонки

**Двойная сессия.** Крон и `/review` могут стартовать одновременно; защита — уникальный частичный индекс `sessions(user_id) WHERE status='active'`. При `IntegrityError` второй процесс молча прекращает создание.

**Устаревшие callback.** Перед любой мутацией проверяется `session.status='active'` и `session_item.answered_at IS NULL` (И-8).

**Двойной тап.** Первый callback получает право на мутацию, второй видит заполненный `answered_at` и не меняет ни рейтинг, ни `review_state`. Мутация выполняется транзакционно.

**Параллельная регенерация.** Два воркера не должны создать два валидных вопроса одного слота; гарантируется частичным уникальным индексом (§3.1).

# 19. Telegram UX

## 19.1 Общие правила

Нативные опросы Telegram не использовать: пояснение ограничено 200 символами, нет единообразия с тремя другими типами заданий, некуда поставить кнопку перехода к источнику.

```python
class Ans(CallbackData, prefix="a"):    # ответ на mcq
    si: int; v: int                      # v = -1: «не знаю»

class Pick(CallbackData, prefix="p"):   # такт выбора в match
    si: int; side: int; idx: int         # side: 0 = левое, 1 = правое

class Act(CallbackData, prefix="x"):    # готово / сброс / подсказка / источник / жалоба
    si: int; op: str
```

Промежуточное состояние соотнесения хранится в `session_items.user_state`; FSM источником истины не является, потому что должно переживать рестарт воркера.

`answer_callback_query` вызывается до редактирования сообщения. `MessageNotModified` перехватывается и игнорируется — при быстрых тапах он неизбежен.

## 19.2 Рендеринг

`parse_mode=HTML`, `html.escape`, белый список тегов. Markdown от модели регулярно невалиден для Telegram.

## 19.4 Ответ на неподдерживаемый ввод — переходное требование

**Этот раздел временный.** Он описывает поведение на тех пакетах работ, где бот уже отвечает пользователю, но ещё не умеет принимать материалы. Вместе с WP-03 раздел и константа `UNSUPPORTED_REPLY_COOLDOWN_SEC` удаляются.

Сообщение, не обработанное ни одним хендлером, не отбрасывается молча. Пользователь получает короткий ответ, сообщающий две вещи: приём материалов пока не готов и **файл не сохранён**. Вторая часть обязательна — без неё человек решит, что файл в очереди, и будет ждать.

Ответ выдаётся не чаще одного раза в `UNSUPPORTED_REPLY_COOLDOWN_SEC` на пользователя: альбом из десяти фотографий приходит десятью отдельными сообщениями, и перехватчик без ограничения ответил бы десять раз. Счётчик — в Redis с ключом по `user_id` и временем жизни, равным окну, тем же механизмом, что троттлинг §31.

Тип неподдерживаемого сообщения пишется в лог — `photo`, `document`, `voice`, `text`. Содержимое не логируется. Это даёт основания для приоритизации: если пользователи присылают преимущественно фотографии, порядок работ по источникам стоит пересмотреть.

**Причина требования.** Тишина в ответ на файл неотличима от зависшего бота, пропавшей сети или блокировки, а текст согласия (§31) прямо приглашает прислать материал. Молчание после приглашения — противоречие внутри одного экрана, а не недоработка дорожной карты.

## 19.3 Формулы

Простое — юникодом (`x²`, `∑`, `→`). Сложное — PNG через matplotlib `mathtext`. Если рендеринг не удался, показывается исходный LaTeX в `<code>`, а не падает обработчик.

# 20. Типы заданий

**MCQ.** Вопрос и пронумерованные варианты в тексте; клавиатура `1 2 3 4` одним рядом плюс `🤷 Не знаю`.

**Open.** Вопрос, FSM `waiting_open_answer`, кнопки `💡 Подсказка` и `🤷 Не знаю`.

**Match text.** Двухтактный выбор, состояние отражается в тексте сообщения:

```
Соотнесите термин и определение:

1. Митоз → B
2. Мейоз → ?
3. Амитоз → ?

A. деление без веретена
B. деление с сохранением набора хромосом
C. редукционное деление
```

Клавиатура: ряд несопоставленных левых (выбранный помечен `•2•`), ряд доступных правых, `↩️ Сброс`, `✅ Готово`. Два тапа — одна пара.

**Match image.** `send_media_group` (не более 10) с подписями `1`, `2`, `3`, затем отдельное сообщение с управлением: медиагруппу нельзя редактировать. `tg_file_id` сохраняется в `media_assets` после первой отправки и переиспользуется.

Идентификаторы сообщений хранятся раздельно: сообщение управления — в `sessions.control_message_id`, идентификаторы сообщений медиагруппы — в `session_items.user_state.media_message_ids`. Одного поля здесь не хватает: по завершении задания медиагруппу нужно убрать или оставить без клавиатуры, а редактировать и удалять её можно только поимённо. Хранение в `user_state` выбрано по той же причине, что и промежуточное состояние соотнесения, — оно обязано пережить рестарт воркера (§19.1).

# 21. Проверка ответа

## 21.1 MCQ и соотнесения

Программно, без вызова модели.

## 21.2 Открытый ответ, ступень 1

Нормализация: NFKC → lowercase → `ё → е` → схлопывание пробелов → удаление финальной пунктуации.

**Guard на отрицание.** Сравнение ведётся с эталоном и каждым элементом `accept`; guard применяется к тому кандидату, который дал наибольший балл. Если симметрическая разность множеств токенов ответа и этого кандидата содержит токен из списка отрицаний (`не`, `нет`, `ни`, `без` и эквиваленты для языка материала, конфигурируется), ступень 1 пропускается и вызывается судья.

**Метрика.** Используется `rapidfuzz.fuzz.WRatio` против `reference` и каждого элемента `accept`. Результат `≥ FUZZY_ACCEPT_THRESHOLD` даёт `correct` без вызова модели.

**Почему не `token_set_ratio`.** Эта метрика по устройству нечувствительна к лишним токенам: она сравнивает пересечение множеств, поэтому ответ «митоз **не** сохраняет набор хромосом» против эталона «митоз сохраняет набор хромосом» отличается одним токеном и набирает около 95. Перевёрнутый по смыслу ответ был бы засчитан как верный, причём судья не вызвался бы вовсе. Это тот же провал, из-за которого `must_include` лишён права на автоматический вердикт, — на шаг раньше в конвейере.

## 21.3 Открытый ответ, ступень 2: судья

Вход: эталон, `must_include` как подсказка, текст исходных фрагментов, ответ пользователя.

```json
{"verdict":"correct|partial|wrong","feedback":"одна фраза"}
```

Судья оценивает только по представленному evidence, не использует внешние знания, учитывает смысл, а не совпадение слов, снисходителен к опечаткам и синонимам, строг к смысловой подмене и путанице терминов. `must_include` не является автоматическим условием правильности.

## 21.4 Спорный случай

При вердикте `partial` показывается эталон и две кнопки `[Засчитать]` / `[Не засчитать]`. Выбор определяет рейтинг (`Hard` или `Again`) и пишется в `review_logs`.

Модератора в персональном боте не существует, поэтому арбитраж выполняет сам пользователь. Это честнее автоматического решения и даёт данные для калибровки судьи — именно на спорных ответах он ошибается чаще всего, а каждая такая ошибка портит расписание факта на недели вперёд.

# 23. Переход к источнику

| Источник | Действие |
|---|---|
| YouTube | `https://youtu.be/{id}?t={int(start)}` |
| Загруженное видео | `ffmpeg -ss {start-15} -t 30` → клип как video, подпись `14:33` |
| Аудио | фрагмент `start-15 … end+15` как voice |
| PDF | подсветка **для каждого** `fragment_id` факта, рендер страниц в PNG 150 dpi |
| Веб | `{url}#:~:text={urlencode(quote)}` |
| Изображение | исходник по `tg_file_id`; если он ещё `NULL` — отправка файла с диска по `media_assets.path` с сохранением полученного `tg_file_id`; при наличии `region` — с рамкой |

Для PDF важно именно «каждого»: факт регулярно опирается на два-три фрагмента, и подсветка только первого показывает половину обоснования. Если фрагменты лежат на разных страницах, отправляются все соответствующие страницы.

Фолбэк по изображению обязателен, а не желателен: `tg_file_id` заполняется только после первой отправки ассета в чат (§20), а переход к источнику регулярно оказывается этой первой отправкой — например, когда факт опирается на схему со страницы PDF, а задания типа `match_image` по нему ещё не выдавались. Без фолбэка переход падал бы именно на первом использовании.

Клипы кешируются по `(material_id, start)`: повторная ошибка на том же факте не запускает ffmpeg заново.

# 24. Контроль качества

## 24.1 Жалобы

Кнопка `⚠️` у каждого вопроса:

```
⚠️ Вопрос непонятен
📖 Не вижу ответ в источнике
❗ Неверный правильный ответ
📝 Ошибка в конспекте
```

Внутренне поддерживаются также `duplicate`, `wrong_difficulty`, `technical`. Жалоба пишется в `quality_reports` и никогда не меняет базу знаний автоматически.

## 24.2 Жалоба на вопрос

Вопрос переводится в `rejected` и немедленно исключается из ротации; факт остаётся в FSRS; ставится задача регенерации (§12). На следующем повторении факт выдаст другой вопрос (§13.3).

## 24.3 Жалоба на evidence

Запускается отдельная переверификация: факт и тексты его фрагментов подаются модели, ответ — `confirmed`, `not_confirmed` или `ambiguous`. При `not_confirmed` факт переводится в `suspended` и исключается из SRS.

Детерминированная проверка вместо вычитания фиксированной величины из `confidence`: арифметика на магическом числе давала разное число жалоб до срабатывания в зависимости от стартового значения.

## 24.4 Жалоба на конспект

Секция помечается; перегенерация запускается только по явному запросу пользователя.

# 25. Метрики качества

В `/stats`, раздел «Качество» — нужны для отладки промптов, а не для пользователя:

7. оценка против факта по токенам и по стоимости;
8. среднее число попыток регенерации;
9. число фактов с `generation_status = 'unavailable'`;
10. распределение вопросов по `(type, direction)`.

# 31. Безопасность

Изоляция по `user_id` в каждом запросе — не полагаться на то, что пользователь один. Лимит размера файла. MIME определяется по содержимому, а не по расширению.

**Rate limiting в middleware.** Не более `THROTTLE_MESSAGES` входящих сообщений от одного пользователя за `THROTTLE_WINDOW_SEC` секунд. Счётчики хранятся в Redis с ключом по `user_id` и временем жизни, равным окну: так они переживают рестарт процесса и не требуют отдельной очистки. При превышении пользователь получает одно предупреждение за окно, последующие сообщения игнорируются молча.

Назначение этого ограничения — не защита от атаки: доступ и так закрыт белым списком (§1.3). Оно отсекает случайный цикл, зажатую кнопку и повторную отправку одного файла, каждая из которых иначе запускает обработку материала заново и расходует бюджет §6.3.

Троттлер §17.3, ограничивающий **исходящие** сообщения примерно одним в секунду на чат, — другой механизм с другой целью и вводится в §17.

Логи в structlog JSON с `user_id` и `material_id` в контексте; полный текст учебных материалов в логи не попадает, максимум первые 80 символов там, где это действительно необходимо.

Необработанное исключение: пользователь получает безопасное сообщение, трейс уходит в лог, процесс бота не падает.

Согласие на обработку данных фиксируется при первом запуске (`users.consent_at`).

# 34. Этапы и приёмка

## Этап 1 — полный учебный цикл на PDF и изображениях

```
загрузка → fragments → facts (+confidence) → notes (3 режима)
→ 4 типа заданий → validator → FSRS → planner → interleaving
→ проверка ответа → разбор → ссылка на источник → mastery
→ каталог → быстрое повторение → жалобы → регенерация
```

Четыре типа заданий доступны сразу: изображения из PDF и отдельные картинки дают материал для `match_image`.

### Приёмка

**Производительность.** Норматив не назначается умозрительно, а выводится из замеров спайка — см. §34.1. Норматив v3.4 («текстовый PDF на 30 страниц — менее 5 минут») арифметически недостижим и заменён.

**Evidence.** 100% валидных вопросов имеют разрешимую ссылку: автотест обходит всю таблицу `questions` и строит ссылку по цепочке `question → fact → fragment → locator`.

**Качество заданий.** Доля отклонённых валидатором не превышает 25% на наборе из трёх материалов при первом запуске и 15% после настройки промптов по размеченным заказчиком примерам. Верхний порог смягчён относительно v3.1 сознательно: у ряда провайдеров структурированный вывод менее стабилен, и требовать сразу 15% значит застрять на настройке промптов вместо продвижения по этапам. Ни один отклонённый вопрос не попадает в сессию.

**Регенерация.** После отклонения новый вопрос может занять тот же `(fact, type, direction)`. После исчерпания попыток система не уходит в бесконечный цикл, факт помечается `unavailable` и пропускается планировщиком.

**Сессия.** Из 6 заданий минимум 3 разных типа; нет 3 подряд одного типа и 3 подряд из одной секции — при условии, что доступный набор это позволяет.

**Планировщик.** После завершения обработки у каждого обучаемого факта появляется строка `review_states`; первая сессия приходит примерно через 10 минут. Повторная обработка того же материала не сбрасывает уже накопленное расписание. Тихие часы работают и внутри дня, и через полночь. Дневной лимит считается по отвеченным заданиям: брошенная сессия его не расходует.

**Источник.** Ошибка на PDF показывает нужную страницу с подсветкой; при нескольких фрагментах факта подсвечиваются все.

**Mastery.** При `coverage < 0.5` значение не превышает 0.5. При сдвиге времени на 14 дней без новых ответов mastery не меняется, freshness падает. Брошенная до ответа сессия не меняет ни coverage, ни FSRS.

**Важность.** Юнит-тест: факт с `importance = 3` попадает в краткий режим конспекта и в раздел «Что запомнить»; факт с `importance = 1` — только в подробный. Тот же тест проверяет, что в формуле strength он весит втрое больше.

**Открытый ответ.** Юнит-тест: ответ, отличающийся от эталона только отрицанием, не засчитывается на ступени 1 и уходит к судье.

**Выбор вопроса.** Факт с двумя вопросами одного типа всё равно получает вопрос. Вопрос со сложностью выше cap не выбирается, если подходящий существует; при отсутствии работает откат §13.3.

**Восстановление.** После `docker compose down && up` не теряются расписание, незавершённые сессии, состояние соотнесения, факты и вопросы. Искусственный сбой внутри каждой стадии корректно восстанавливается и не оставляет дубликатов.

**Гонки.** Одновременные `/review` и срабатывание крона создают ровно одну активную сессию. Двойной callback не создаёт два журнала. Callback завершённой сессии не меняет данные.

**Жалобы.** Жалоба немедленно убирает вопрос из ротации и создаёт задачу регенерации; отклонённый вопрос не блокирует слот.

**Стоимость.** `cost_estimate` создаётся **до стадии `extract`** и содержит валюту (§6.3); уточнённая после `extract` оценка отклоняется от факта не более чем на 40%. Материал, обработанный в режиме `notes_only`, в этой проверке не участвует.

**Режим «только конспект».** Материал с `mode = 'notes_only'` достигает статуса `ready`, не имеет ни одной строки `review_states`, показывается как «конспект без заданий», и кнопка «Достроить задания» доводит его до полного состояния без переобработки уже выполненных стадий.

**Дневная норма новизны.** `new_per_day` расходуется только отвеченными новыми фактами; брошенная сессия её не тратит; при исчерпании нормы повторения продолжают приходить.

## 34.1 Калибровка норматива производительности

Время обработки определяется не кодом, а числом вызовов модели и разрешённым параллелизмом:

```
T ≈ (N_секций + N_фактов × 2) / LLM_CONCURRENCY × t_вызова
```

Множитель `2` — это один вызов генерации (§10.1) и один вызов валидатора (§11.4) на каждый факт. Оба решения приняты сознательно и не пересматриваются: генерация набора одним вызовом даёт разнообразие по построению, валидатор обязателен (§0.2).

Подставив реальные значения — 30 страниц текстового учебника дают порядка 60–120 фактов, то есть 120–240 вызовов, — при `LLM_CONCURRENCY = 4` и типичных 10–15 секундах на вызов получаем 15–25 минут. Пятиминутный норматив v3.4 не мог быть выполнен ни при какой реализации, и попытка его достичь означала бы отказ от валидатора или батчинг фактов в один вызов, то есть откат решений §0.2.

Порядок калибровки:

1. На спайке (до начала разработки) измеряются `t_вызова` для генерации и для валидации на реальном материале, а также фактическое число фактов на страницу.
2. `LLM_CONCURRENCY` выставляется по лимитам выбранного провайдера — стартовое значение 16.
3. В настоящий раздел вносится норматив, посчитанный по формуле, с запасом 1.5×. Он фиксируется до начала этапа 1 и дальше является критерием приёмки наравне с остальными.

До выполнения шага 3 норматив производительности считается неустановленным, и приёмка по нему не проводится. Это единственный критерий §34, которому разрешено отсутствовать на старте.

## 34.2 Главная продуктовая метрика

Accuracy на интервалах 7 и 30 дней (§1.1, §29) за две недели приёмки измерить нельзя. Но её вычисление проверяемо и проверяется обязательно: юнит-тест подаёт синтетический набор `review_logs` с известными `elapsed_days` и вердиктами и сверяет посчитанные доли с ожидаемыми, включая вырожденные случаи — нет ни одного повторения на интервале, все повторения на границе интервала, повторения только со вердиктом `skipped`.

Без этого теста главный показатель системы не покрыт ничем: ошибка в его арифметике проявится через месяц эксплуатации и будет неотличима от плохой педагогики.

## Этап 2 — аудио и видео

faster-whisper, ffmpeg, PySceneDetect, `scene_id`, сшивка слайда и транскрипта, таймкоды, клипы, YouTube-ссылки.

Приёмка: лекция 60 минут обрабатывается менее чем за 15 минут на целевом железе; клип начинается не более чем за 20 секунд до нужного момента; ссылка на YouTube открывается на нужной секунде; сбой после распознавания речи не требует повторного распознавания, если стадия `extract` уже закоммичена.

Планирование под дедлайн и предельный интервал §13.1 связаны: потолок — грубая и дешёвая мера, дедлайн — точная. При появлении второго первый становится его частным случаем.

# 36. Тесты

**Юнит.** Вырожденные случаи mastery (нет пройденных фактов, нет обучаемых фактов); идемпотентность стадии `schedule`; предикат обучаемости на всех комбинациях флагов; подсчёт `daily_cap` на границе локальных суток; подсчёт `new_per_day` по `introduced_at` на границе локальных суток и его нерасходование брошенной сессией; вычисление accuracy на интервалах 7 и 30 дней на синтетических `review_logs` (§34.2); валидаторы схемы вопроса; лексическая утечка; биекция пар; шкала важности (§34); выбор по сложности; `Locator`; построение ссылки на источник; соответствие рейтингов; mastery и её инвариантность ко времени; определение `seen`; откат выбора вопроса; регенерация; поведение частичного уникального индекса; сборщик сессии и interleaving; тихие часы; пагинация и лимит 4096 по отрендеренному HTML; экранирование; guard на отрицание в открытом ответе; валидация callback.

**Интеграционные.** Полный конвейер на фикстурах: текстовый PDF, сканированный PDF, изображение, короткое аудио. Проверяются все стадии от `extract` до планировщика. Отдельно — искусственный сбой посередине каждой стадии.

Отдельными интеграционными сценариями проверяются три перехода, добавленные в v3.5:

- сбой воркера между генерацией и валидацией оставляет `draft`-строки; перезапуск стадии `questions` их удаляет, и слот `(fact_id, type, direction)` снова доступен;
- факт без валидных вопросов на момент стадии `schedule` после успешной регенерации получает строку `review_states` и попадает в ближайшую сессию;
- материал `notes_only` проходит до `ready`, не создаёт `review_states`, а «Достроить задания» доводит его до полного состояния, не переисполняя `extract`, `sections`, `facts` и `notes`.

**Моки.** Вызовы модели мокаются записанными ответами в `tests/golden/*.json`; реальные вызовы — только под маркером `@pytest.mark.live`.

**LLM:** некорректный структурированный вывод; неизвестный `fragment_id`; дублирующиеся вопросы; невалидная пара; двусмысленный ответ; таймаут; 429; 5xx; пустой ответ.

**Telegram:** `RetryAfter`; `MessageNotModified`; двойной тап; устаревший callback; сообщение длиннее 4096.

**База:** дубликат материала; попытка второй активной сессии; конкурентная регенерация; откат после частичной транзакции.

**Обучение:** первая встреча с фактом и неверный ответ; «не знаю»; частичный ответ; верный; быстрый верный; брошенная сессия; приостановленный факт; факт без валидных вопросов.

# 38. Критические свойства

Должны быть доказаны тестами до перехода между этапами:

1. Нельзя получить валидный вопрос без evidence.
2. Нельзя создать две активные сессии одного пользователя.
3. Нельзя изменить FSRS без ответа пользователя.
4. Перегенерация вопроса не ломает историю факта.
5. Нельзя получить два активных вопроса одного `(fact, type, direction)`.
6. Отклонённый вопрос не блокирует регенерацию.
7. Сбой стадии не оставляет частично принятый результат.
8. Старый callback не изменяет данные.
9. Mastery не падает только из-за течения времени.
10. Freshness при этом падать может.
11. Факт с `derived = true` не становится источником обучения в MVP.
12. Идентичность факта стабильна после начала обучения.
13. Ответ, отличающийся от эталона только отрицанием, не засчитывается автоматически.
14. Факт с `importance = 3` весит в mastery больше, чем факт с `importance = 1`.
15. После обработки материала у каждого обучаемого факта есть строка `review_states`, и первая сессия достижима.
16. Повторный запуск стадии `schedule` не сбрасывает накопленное состояние повторения.
17. Секция без пройденных фактов даёт `mastery = 0`, а не ошибку деления.
18. Предикат обучаемости один и тот же в планировщике, в coverage и при создании `review_states`.
19. Успешная регенерация возвращает факт в ротацию: после появления валидного вопроса у факта есть строка `review_states`, даже если на момент стадии `schedule` её не было.
20. Строка `draft`, оставшаяся после сбоя воркера, не блокирует слот `(fact_id, type, direction)` — перезапуск стадии `questions` её удаляет, и новый вопрос создаётся.
21. Материал в режиме `notes_only` достижимо переводится в полный: «Достроить задания» доводит его до состояния, в котором обучаемые факты имеют `review_states`.
22. `new_per_day` расходуется только отвеченными новыми фактами: брошенная сессия дневную норму новизны не тратит.

# 40. Правило разработки

```
спецификация → реализация → unit → integration → ручная проверка → документация → commit
```

Переход к следующему этапу при падающих критических тестах запрещён.

Если реализация обнаруживает противоречие в ТЗ, разработчик **не выбирает вариант самостоятельно**: противоречие фиксируется как change request, обновляется спецификация и соответствующий acceptance-тест, и только после этого пишется код.

Главный критерий системы — не количество созданных конспектов, а доля правильных ответов на увеличенных интервалах при сохранной цепочке evidence у каждого заданного вопроса.

# 41. Процесс разработки: двухагентная схема

Разработка ведётся двумя агентами с разделёнными ролями. Правила процесса входят в ТЗ, потому что иначе они не проверяемы: приёмка по §34 показывает, что система работает, но ничего не говорит о том, каким способом она сделана, а именно способ определяет, можно ли её дальше развивать.

## 41.1 Роли

**Разработчик** — основная сессия агента. Читает задачу и названные разделы ТЗ, пишет План разработчика, получает на него approve, реализует пакет в отдельной ветке, открывает PR, отвечает на замечания. Не выполняет merge.

**Проверяющий** — отдельный агентский контекст. Получает на вход только задачу, План разработчика и дифф — без рассуждений Разработчика. Проходит чек-лист целиком, выносит `approve` / `request-changes` / `reject`, выполняет merge. Код за Разработчика не пишет.

**Архитектор** — заказчик. Арбитр споров, единственный, кто разрешает отступление от жёстких правил, принимает фазы целиком.

Один агентский контекст не может исполнять обе роли в рамках одной задачи. Проверяющий, видевший ход рассуждений Разработчика, соглашается с ними — именно это и делает самопроверку бессмысленной.

## 41.2 Цикл пакета работ

```
Issue со ссылкой на § ТЗ
  → План разработчика → approve плана
  → ветка → реализация → тесты → PR
  → ревью по чек-листу → правки → повторное ревью
  → merge, ветка удаляется
```

**Без approve плана код не пишется.** Двухфазный коммит — режим по умолчанию; однофазный допустим только для задач до 3 файлов и 100 строк без новых сущностей, публичных API и критических путей, и только если план был одобрен без замечаний. Любое замечание при первом ревью переводит задачу в двухфазный режим.

## 41.3 Отношение к §40

§40 запрещает разработчику самостоятельно разрешать противоречия в ТЗ. В двухагентной схеме это правило получает исполнителя: Проверяющий обязан отклонить PR, в котором противоречие ТЗ разрешено кодом, а не change request'ом. Разделы 0.1–0.2 настоящей версии — результат применения этого правила: §0.2 к редакции v3.4, §0.1 к v3.5.

## 41.4 Технические гарантии

Словесных запретов агенту недостаточно: под давлением сроков он найдёт обоснование обходу. Правила дублируются настройками репозитория — запрет прямого push в защищённые ветки, обязательный зелёный CI до merge, обязательный approve, запрет force-push и удаления ветки.

**Осознанное отступление: требование approve снято.** GitHub не позволяет одобрять собственный pull request, а участник репозитория один. Единственным способом выполнить требование был бы обход правила администратором при каждом merge — а правило, нарушаемое систематически, хуже отсутствующего: оно приучает считать настройки репозитория декорацией.

Поэтому обязательный approve не включается, а технически обеспечиваются те гарантии, которые обеспечиваются полностью: запрет прямого push, обязательный зелёный CI, запрет force-push и удаления ветки. Ревью при этом не отменяется — меняется только способ его фиксации: **вердикт Проверяющего публикуется комментарием в PR по шаблону отчёта ревью, и merge без такого комментария считается нарушением §41.2.** Проверить это может человек, а не сервер, и в этом слабость решения.

Отступление снимается добавлением второго участника репозитория: тогда approve становится исполнимым, и требование возвращается.

CI обязан выполнять то же, что требует §35: `ruff`, `black --check`, `mypy --strict` на `core/`, `pytest` в режиме `LLM_MODE=replay` при отключённой сети. Тест, требующий сети, запускается только под `@pytest.mark.live` и в CI не участвует.
