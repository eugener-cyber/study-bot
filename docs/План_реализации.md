# План реализации v3 — Telegram-бот для учёбы

Базовый документ: **ТЗ v3.7**. План задаёт порядок работ, границы пакетов, способ проверки и процесс разработки. Требований ТЗ не дублирует.

**Отличия от v2.** Работы ведутся по двухагентной схеме (§1.1), и это меняет не только процедуру, но и нарезку пакетов: пакет должен быть обозрим для ревью. WP-01 разделён надвое. Переход к источнику поднят с двенадцатого места на шестое — он не зависит от проверки ответов, а без него первая же ошибка в ежедневном использовании не ведёт никуда. Спайк расширен: он измеряет не только извлечение фактов, но и валидатор, судью и время вызова, потому что от последнего зависит норматив производительности §34.1.

---

# 1. Правила работы

**Один пакет — одна ветка — один PR.** Пакет, растянутый на несколько сессий, теряет контекст и начинает противоречить сам себе.

**Опережение запрещено.** «Заодно» сделанный соседний пакет выглядит экономией, но лишает возможности принимать работу частями: первая же ошибка обнаруживается сразу в трёх местах.

**Тесты входят в пакет.** Пакет без тестов из «Готово, если» не считается сданным.

**Противоречия в ТЗ агент не разрешает сам** (§40 ТЗ). Он останавливается и сообщает; решение принимаете вы, правится ТЗ, потом продолжается работа. Проверяющий обязан отклонить PR, в котором противоречие разрешено кодом.

## 1.1 Двухагентная схема

Каждый пакет проходит через два независимых агентских контекста — Разработчика и Проверяющего (ТЗ §41, скилл `two-agent-development`).

```
Issue со ссылкой на § ТЗ и «Готово, если»
  → План разработчика          (артефакт, публикуется до первой строки кода)
  → approve плана Проверяющим
  → ветка wp-07-fact-extraction → реализация → тесты → PR
  → ревью по чек-листу → правки → повторное ревью
  → merge Проверяющим, ветка удаляется
```

**Без approve плана код не пишется.** Двухфазный коммит — режим по умолчанию. Однофазный возможен только для мелких пакетов (до 3 файлов и 100 строк без тестов, без новых сущностей и критических путей) и только при плане, одобренном без замечаний. В этом плане под однофазный режим не подходит ни один пакет фазы 1.

Проверяющий получает на вход задачу, План разработчика и дифф — и ничего из рассуждений Разработчика. Иначе он соглашается с тем, что уже прочитал.

Вы принимаете работу по диффу, по отчёту ревью и по выводу `make`-команд из «Готово, если», а не по описанию от агента.

**Размер PR.** Регламент требует до 400 строк, максимум 800. WP-01 и WP-02 в этот предел не укладываются и идут по штатному исключению «первичная структура нового модуля, миграции» — это фиксируется в Issue заранее, а не объясняется постфактум. Все остальные пакеты в предел укладываются; если не укладываются, значит границы пакета определены неверно.

## 1.2 Начало сессии

```
Прочитай CLAUDE.md и ТЗ_v3.7.md §4, §4.6, §14.3.
Работаешь в роли Разработчика по двухагентной схеме.
Реализуй WP-12 из План_реализации_v3.md. Границы пакета не расширяй, ТЗ не меняй.
Сначала План разработчика — код после approve.
Закончи тестами из «Готово, если» и обнови STATE.md.
```

Перечисление конкретных разделов обязательно: без него агент прочитает весь документ и потратит контекст на нерелевантное.

## 1.3 Два файла, которые агент читает всегда

**`CLAUDE.md`** в корне репозитория, не длиннее полутора страниц. Создаётся в WP-01 и меняется редко:

- десять инвариантов §1.2 ТЗ в одну строку каждый;
- предикат обучаемости словами и ссылка на реализацию;
- конвенции: где бизнес-логика, где хендлеры, как пишутся миграции, чем запускаются тесты;
- запрет на изменение ТЗ и порядок change request;
- команды харнесса (§1.4);
- ссылка на двухагентный регламент и на список костылей.

**`STATE.md`** — короткая сводка: какие пакеты сданы, что в работе, какие решения приняты по ходу, какие вопросы открыты. Обновляется последним действием каждой сессии. Без него сессия N+1 заново выводит то, что уже решено в сессии N.

## 1.4 Харнесс разработчика

Агент не видит Telegram и не может проверить работу вручную. Поэтому с первого пакета существует консольный интерфейс, покрывающий весь цикл:

```
make reset                   пересоздать БД и накатить миграции
make seed FILE=...           прогнать материал через конвейер целиком
make dump-material ID=...    фрагменты, факты, вопросы в читаемом виде
make session USER=...        собрать сессию и отрисовать её текстом
make answer ITEM=... A=...   ответить за пользователя, показать вердикт и разбор
make cite QUESTION=...       построить ссылку на источник и сохранить результат
make evals                   прогнать эталонный набор промптов, напечатать долю отбраковки
make check                   ruff + black --check + mypy --strict core/ + pytest
```

Это не вспомогательный инструмент, а основной способ разработки: почти все проверки «Готово, если» выполняются через него. `make check` — то же, что делает CI, чтобы красный CI не был открытием на этапе PR.

## 1.5 Запись и воспроизведение вызовов модели

Тесты не ходят в сеть, но моки нельзя писать руками — сочинённый JSON не похож на реальный вывод модели, и ошибки промптов прячутся до продакшена.

```
LLM_MODE=record   реальный вызов, ответ пишется в tests/golden/<purpose>/<hash>.json
LLM_MODE=replay   значение по умолчанию, сеть недоступна, ответ берётся из файла
LLM_MODE=live     только под @pytest.mark.live
```

Ключ записи — хеш от (версия промпта, схема, вход). Смена версии промпта автоматически делает старые записи недействительными, и это видно по падению тестов, а не по странному поведению.

**Записи спайка становятся первыми golden-фикстурами.** Иначе первые реальные ответы модели выбрасываются и записываются заново в WP-04.

# 2. Шаг 0. Спайк провайдера

**До начала разработки, один день.** Отдельный скрипт вне будущей архитектуры, на реальном материале. Расширен относительно v2: там спайк проверял только извлечение фактов, но извлечение — не самое рискованное место.

**Вход зафиксирован.** Провайдер — Anthropic Claude API, модель `claude-opus-5` (ТЗ §2.1). Материал — опубликованные ЦПМК требования и задания ВсОШ по труду (технологии), профиль «Культура дома, дизайн и технологии». Первая фикстура уже проверена на пригодность: текстовый PDF на 34 страницы со встроенным текстовым слоем — то есть ровно тот размер, на котором считается норматив §34.1 ТЗ.

Проверяется:

1. держит ли провайдер структурированный вывод по нетривиальной схеме;
2. возвращает ли валидные `fragment_ids` или выдумывает их;
3. насколько осмысленны формулировки фактов на вашем предмете;
4. **справляется ли провайдер с ролью валидатора** (§11.4 ТЗ) — один вызов на набор из 3–4 вопросов, вход включает факт, фрагменты и все вопросы; интересует не только валидность JSON, но и адекватность вердиктов на заведомо битых вопросах, которые подкладываются намеренно;
5. **справляется ли он с ролью судьи** (§21.3) — в частности, отличает ли смысловую подмену от опечатки и не засчитывает ли перевёрнутый по смыслу ответ;
6. **сколько секунд занимает вызов** каждого вида и сколько фактов получается со страницы.

Пункты 4 и 5 добавлены потому, что именно они определяют продуктовое качество: валидатор задаёт коридор отбраковки §34, судья — корректность рейтингов, а значит и всё расписание. Провайдер, хорошо извлекающий факты и плохо судящий, даёт систему, которая уверенно учит неправильному.

Пункт 6 — вход для §34.1 ТЗ: норматив производительности выводится из замеров, а не назначается.

**Выход спайка** — три числа (`t_вызова` для генерации, валидации, судейства), число фактов на страницу, оценка токенов на страницу и заполненный §34.1 ТЗ. Плюс первые golden-записи и первая версия списка стоп-слов §11.2 и отрицаний §21.2 под русский язык и эту предметную область.

**Отдельно проверяется стоимость.** При $5 за миллион входных и $25 за миллион выходных токенов спайк даёт прямую цену обработки одного 34-страничного материала. Из неё выводится `COST_WARN_THRESHOLD` — иначе порог назначается наугад и срабатывает либо на всём, либо ни на чём.

Если провайдер не тянет пункты 1–2, решение принимается здесь: другой провайдер либо упрощение схемы с переносом части работы на программные проверки. Если не тянет 4–5 — вопрос о провайдере, а не о промптах.

# 3. Фаза 1. Сквозной скелет

Цель фазы — работающая насквозь система с заглушками вместо содержания. После неё каждый следующий пакет заменяет одну заглушку на настоящую реализацию и проверяется на живой системе.

## WP-01. Инфраструктура, каркас бота, процесс

Репозиторий на GitHub с защищённой веткой `main`, CI. `docker-compose` на четыре контейнера **включая `telegram-bot-api`**, конфигурация на pydantic-settings, `.env.example`, structlog, middleware авторизации и троттлинга, `/start` с фиксацией согласия, глобальный перехват исключений. `CLAUDE.md`, `STATE.md`, шаблоны Issue и PR, каталог `docs/adr/`.

CI выполняет ровно то же, что `make check`, при отключённой сети.

Защита ветки: запрет прямого push, обязательный зелёный CI, запрет force-push и удаления ветки. Обязательный approve **не включается** — ТЗ §41.4, осознанное отступление: GitHub не позволяет одобрять собственный PR, а участник репозитория один. Вердикт Проверяющего фиксируется комментарием в PR.

*Готово, если:* `docker compose up` поднимает все четыре контейнера; бот отвечает пользователю из белого списка и молча отклоняет остальных; необработанное исключение не роняет процесс и не показывает трейс пользователю; прямой push в `main` отклоняется; CI падает на намеренно внесённой ошибке типов.

*ТЗ:* §2.2, §2.3, §30, §31, §35, §41.

## WP-02. Схема данных и харнесс

Все таблицы §3 ТЗ и все индексы §3.1, включая частичный уникальный по `status = 'valid'`. Новые поля v3.5: `materials.mode`, `review_states.created_at` и `introduced_at`, `sessions.control_message_id`. Предикат обучаемости §14.3 — одной SQL-функцией или view. Alembic. Makefile с командами §1.4.

*Готово, если:* `make reset` отрабатывает; каждая миграция откатывается; юнит-тест предиката обучаемости покрывает все комбинации флагов; второй активный сеанс пользователя падает на индексе; отклонённый вопрос не блокирует слот; **строка `draft` не блокирует слот** (свойство §38 №20).

*ТЗ:* §3, §3.1, §14.3.

## WP-03. Загрузка материала и машина стадий

Приём файла через локальный Bot API, `sha256`, дубликаты, `materials` со статусами и `completed_stages`, атомарность стадий с временной директорией, редактируемое сообщение прогресса, механизм `awaiting_user`, бюджетный гейт на `probe` и режим `notes_only` с кнопкой «Достроить задания».

Тесты на восстановление после сбоя пишутся **здесь**, а не в конце: машина стадий строится сейчас, и проверять её через двенадцать пакетов — значит двенадцать пакетов строить на непроверенном допущении.

*Готово, если:* файл больше 20 МБ принимается; дубль показывает существующий материал; искусственный сбой в середине каждой стадии не оставляет частичных артефактов и не меняет `completed_stages`; ожидание ответа пользователя не блокирует воркер; **гейт бюджета срабатывает до `extract`, а не после**; материал `notes_only` доходит до `ready` с `questions:skipped` и достраивается кнопкой без переисполнения ранних стадий; `make seed` доводит материал до `ready` на заглушках.

*ТЗ:* §2.2, §4, §6.3.

## WP-04. LLM-слой с записью и воспроизведением

Интерфейс `LLMProvider`, одна реализация, структурированный вывод, ретраи, семафор `LLM_CONCURRENCY`, `llm_calls` с версией промпта, валютой и фактическими токенами, каталог промптов с версиями в именах, режимы record/replay/live.

*Готово, если:* ответ валидируется схемой; ошибка схемы вызывает ровно один повтор; все вызовы попадают в `llm_calls` с ненулевыми токенами; в режиме replay тесты проходят при отключённой сети; смена версии промпта делает старые записи недействительными; записи спайка воспроизводятся.

*ТЗ:* §2.1, §6.

## WP-05. Сквозной скелет

Самый важный пакет фазы. Конвейер проходит целиком на заглушках: PDF даёт один фрагмент, один захардкоженный факт, один MCQ, стадия `schedule` создаёт состояние, планировщик собирает сессию из одного задания, пользователь отвечает, получает разбор и ссылку на страницу.

Заглушки настоящие по форме и фальшивые по содержанию: они возвращают корректные структуры, но не вызывают модель.

*Готово, если:* `make seed` → `make session` → `make answer` проходит без Telegram и печатает разбор; тот же путь работает в чате; после `docker compose down && up` состояние не теряется; критические свойства §38 №15 и №16 доказаны.

С этого момента есть что показать и на чём проверять всё остальное.

# 4. Фаза 2. Содержание

Каждый пакет заменяет одну заглушку. Порядок выбран так, чтобы первым появилось то, что видит пользователь, и чтобы цепочка evidence замкнулась раньше, чем начнётся ежедневное использование.

## WP-06. PDF-адаптер

Текст с координатами, детект скана и путь через vision, склейка фрагментов, извлечение изображений, заголовки, `fragments.quality`, локаторы PDF и изображений. Реальный `probe`: число страниц и доля страниц, требующих vision, — вход для гейта WP-03.

*Готово, если:* на фикстуре текстового PDF получаются фрагменты с разрешимыми локаторами; сканированный даёт осмысленный текст; каждый локатор превращается в подсвеченную страницу; `probe` даёт оценку до `extract`; `make dump-material` показывает результат читаемо.

*ТЗ:* §5.1–5.3, §3.4, §6.3.

## WP-07. Секции и факты

Группировка в секции, `MAX_SECTION_TOKENS` с семантическим разбиением, извлечение фактов, четыре проверки evidence, итоговая confidence, дедуп, метрика доли `derived`.

Здесь же создаётся **эталонный набор для промптов**: 30–40 фактов из вашего реального материала с разметкой «годится / не годится». `make evals` печатает по нему долю брака. Дальше правка промптов измерима.

*Готово, если:* факт с посторонним `fragment_id` отбрасывается, и это покрыто тестом; факты ниже порога confidence сохраняются, но не идут в генерацию; при превышении доли `derived` приходит предупреждение; `make evals` работает.

*ТЗ:* §6.2, §7.

## WP-08. Конспект

Сборка из фактов, три режима глубины, навигация, пагинация по отрендеренному HTML, выгрузка в `.md` и `.pdf`.

Поставлен рано намеренно: это первое, что вы сможете реально читать и оценивать по существу.

*Готово, если:* факт с важностью 3 попадает в краткий режим и в «Что запомнить», с важностью 1 — только в подробный; сообщение с обилием экранируемых символов не превышает лимит; переключение режима не вызывает модель.

*ТЗ:* §3.2, §8, §19.2.

## WP-09. Генерация вопросов

Один вызов на факт, четыре типа, проверка структуры набора, `generation_status`.

*Готово, если:* набор содержит минимум два разных типа либо факт помечен `single_format`; `match_image` появляется только при наличии подходящих изображений; `make dump-material` показывает вопросы всех типов.

*ТЗ:* §9, §10.

## WP-10. Валидация и регенерация

Проверки отдельного вопроса, валидатор одним вызовом на набор, регенерация с ограничением попыток, недоступность слота как производное состояние, **вызов `ensure_review_states` при успешной регенерации**.

**Здесь потребуется ваше участие:** отсмотреть 20–30 заданий и разметить брак. Разметка пополняет эталонный набор, и коридор отбраковки §34 сходится по `make evals`, а не по ощущениям.

*Готово, если:* доля отбраковки в коридоре §34 на трёх материалах; ни один отклонённый вопрос не выдаётся; после исчерпания попыток нет зацикливания; отклонённый освобождает слот; **факт без валидных вопросов на момент `schedule` после успешной регенерации получает строку `review_states`** (свойство §38 №19).

*ТЗ:* §11, §12.

## WP-11. Переход к источнику

Подсветка всех фрагментов факта, рендер страниц, кеш, фолбэк по `tg_file_id`, ссылки для остальных типов источников.

**Поднят с двенадцатого места на шестое.** Он не зависит ни от FSRS, ни от проверки ответов — только от локаторов (WP-06) и фактов (WP-07). Поставленный здесь, он замыкает цепочку evidence сразу после появления вопросов: автотест §34 проходит по всей таблице `questions` и строит ссылку для каждого, то есть И-1 проверяется на две трети плана раньше. Кроме того, к началу ежедневного использования (WP-15) переход уже работает, а без него первая же ошибка не ведёт никуда — именно за этим и нужен разбор.

*Готово, если:* автотест проходит по всем валидным вопросам и строит ссылку для каждого — ровно 100%; факт с несколькими фрагментами даёт все подсветки; изображение открывается и при пустом `tg_file_id`.

*ТЗ:* §23, §25 п. 2.

## WP-12. FSRS и планирование

Настоящая обёртка над `py-fsrs` вместо заглушки, соответствие результатов рейтингам, `review_logs` с версиями алгоритмов, идемпотентность стадии `schedule` на реальных объёмах, проставление `introduced_at`, **предельный интервал `MAX_INTERVAL_DAYS`** (CR-E1).

*Готово, если:* первая ошибка при `reps = 0` не увеличивает `lapses`; журнал пишется на каждый ответ; повторная обработка материала не сбрасывает накопленное расписание; `introduced_at` проставляется ровно один раз и вместе с `seen`; **длинная серия верных ответов не даёт `due_at` дальше `MAX_INTERVAL_DAYS` от текущего момента** — без потолка восьмое повторение приходится на 12180-й день.

*ТЗ:* §4.6, §13.1, §13.2, §14.2.

## WP-13. Планировщик и сессии

Четыре корзины, interleaving, тихие часы через полночь, `daily_cap` и `new_per_day` по локальным суткам, `MIN_PUSH_INTERVAL`, брошенные сессии, защита от двойной сессии.

*Готово, если:* сессия из шести заданий содержит не менее трёх типов без трёх подряд одинаковых; тихие часы корректны в обоих направлениях; одновременные крон и `/review` дают ровно одну сессию; брошенная сессия не меняет FSRS, не расходует дневной лимит и **не расходует `new_per_day`** (свойство §38 №22); при исчерпанном `new_per_day` повторения продолжают приходить.

*ТЗ:* §16, §16.1, §17, §18.

## WP-14. Интерфейс четырёх типов

Задания в чате, фабрики callback, состояние соотнесения в БД, медиагруппа с хранением `media_message_ids`, `MessageNotModified`, инвалидация старых callback.

*Готово, если:* состояние соотнесения переживает рестарт; двойной тап не создаёт два журнала; кнопки завершённой сессии не меняют данные; ни один `callback_data` не длиннее 64 байт; медиагруппа завершённого задания корректно убирается.

*ТЗ:* §19, §20, §18.

## WP-15. Проверка ответов

Программная проверка, две ступени открытого ответа с guard на отрицание, судья, арбитраж при частичном ответе, разбор из `detail` с уже работающей кнопкой перехода к источнику.

*Готово, если:* ответ, отличающийся от эталона только отрицанием, не засчитывается автоматически и уходит к судье; арбитраж пишется в журнал; разбор не вызывает модель.

*ТЗ:* §21, §22.

**С этого момента начинается ежедневное использование.** Оставшиеся пакеты делаются параллельно с ним.

## WP-16. Mastery, адаптивность, статистика

Формула с вырожденными случаями, freshness, слабые темы, cap по сложности и `desired_retention`, экран прогресса с покрытием банка, accuracy на интервалах 7 и 30 дней.

*Готово, если:* секция без пройденных фактов даёт ноль, а не ошибку; сдвиг времени на 14 дней не меняет mastery, но снижает freshness; при покрытии ниже половины mastery не выше 0.5; рядом с процентом видно число фактов с заданиями; **юнит-тест accuracy на синтетических `review_logs` проходит**, включая вырожденные случаи (§34.2).

*ТЗ:* §14, §15, §29, §34.2.

## WP-17. Каталог, поиск, жалобы

Дерево навигации, загрузка без команды, быстрое повторение, полнотекстовый поиск, кнопка жалобы, переверификация факта, метрики качества.

*Готово, если:* жалоба убирает вопрос из ротации немедленно и ставит регенерацию; переверификация переводит неподтверждённый факт в `suspended`; метрики §25 отображаются; при потере последнего валидного вопроса покрытие банка в §29 меняется одновременно с процентом (§14.3).

*ТЗ:* §24, §25, §26, §27, §28.

## WP-18. Сквозные отказы и гонки

Остаток §37: отказы модели, отказы Telegram, конкурентная регенерация, лимиты. Восстановление после сбоя стадий уже покрыто в WP-03.

*Готово, если:* все двадцать два критических свойства §38 доказаны тестами.

*ТЗ:* §36, §37, §38.

# 6. Приёмка этапа 1

Автоматическая часть — §34 ТЗ целиком, включая норматив производительности, зафиксированный по §34.1 после спайка.

Ручная, которую нельзя заменить тестами:

1. Загрузить реальный учебный PDF и прочитать конспект целиком. Он должен годиться для подготовки, а не быть пересказом оглавления.
2. Дождаться первой автоматической сессии, не вызывая её вручную.
3. Ответить неверно и убедиться, что подсветка ведёт именно туда, где написано обоснование.
4. Пользоваться ежедневно две недели.

Четвёртый пункт начинается после WP-15, а не после WP-18, и идёт параллельно оставшимся пакетам. Ошибки педагогики не видны на демонстрации, только на дистанции, и чем раньше начнётся дистанция, тем дешевле правки.
