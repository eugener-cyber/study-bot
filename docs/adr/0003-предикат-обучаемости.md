# ADR-0003: Предикат обучаемости как функция с параметром порога

**Дата:** 2026-10-06
**Статус:** accepted
**Затрагивает модули:** `core/db/teachable.py`, `alembic/versions/0002_teachable.py`, будущие `core/services` планировщика (§16) и статистики (§14.1), стадия `schedule` (§4.6)

## Контекст

ТЗ §14.3 определяет обучаемый факт пятью условиями и требует: «Реализуется одним SQL-предикатом или view, а не тремя похожими условиями в разных модулях — расхождение между ними даёт факты, которые числятся в статистике, но никогда не выдаются, либо наоборот».

Одно из пяти условий содержит порог: `final_confidence >= MIN_FACT_CONFIDENCE`. Преамбула §30.3 требует, чтобы такие значения оставались константами конфигурации: «Это ровно те числа, которые придётся крутить после первых материалов».

Величина `final_confidence` в §3 не хранится: §7.3 определяет её как `confidence × min(fragment.quality)`.

## Решение

**Set-returning SQL-функция `teachable_facts(min_confidence real)`**, объявленная `LANGUAGE sql STABLE`. Порог подставляет единственная обёртка `core/db/teachable.py` из `Settings`.

**Тип параметра — `real`, не `double precision`.** §3 объявляет оба множителя `REAL`. Произведение считается в float4, и повышение до float8 ради сравнения вскрывает ошибку представления: факт ровно на пороге перестаёт быть обучаемым. Прогон на живом Postgres:

| Порог | Сравнение в `double precision` | Сравнение в `real` |
|---|---|---|
| 0.55 | да | да |
| 0.65 | **нет** | да |
| 0.7 | **нет** | да |
| 0.9 | **нет** | да |

Дефолт 0.55 в ложь не попадает — поэтому тест на одном дефолте был бы зелёным по совпадению, а сломалось бы у заказчика после правки `.env`. Тест параметризован по всем четырём значениям.

Привязка параметра идёт как `CAST(:min_confidence AS real)`. Приведение float8 → real в Postgres имеет уровень assignment, не implicit, и вызова `teachable_facts(0.65::double precision)` не существует; порог же приходит из `Settings` как Python float.

**`COALESCE` стоит в списке колонок, но не в условии отбора.** Это исправление дефекта, найденного мутационным прогоном уже после написания функции. С `COALESCE` в условии при `MIN_FACT_CONFIDENCE = 0` произведение давало `0 >= 0`, и факт без evidence становился обучаемым — нарушение И-1 (§7.3 проверка 1). Теперь `MIN` по пустому множеству, по несуществующим идентификаторам или по `NULL` в `quality` даёт `NULL`, и строка отбрасывается при любом пороге.

**Неизвестное качество части evidence игнорируется, и это зафиксировано, а не выбрано.** `MIN` в SQL пропускает `NULL`, поэтому факт с фрагментами `quality = 1.0` и `quality = NULL` обучаем с `final_confidence = 1.0` — как будто второго фрагмента нет. То же с битой ссылкой: `MIN` считается по найденным идентификаторам.

Вырожденные случаи ведут себя иначе: когда **все** фрагменты неизмерены или **все** ссылки битые, `MIN` даёт `NULL`, и факт исключается при любом пороге. Асимметрия между смесью и вырожденным случаем найдена ревью PR #10 и закреплена тестами `test_mixed_quality_ignores_the_unmeasured_fragment` и `test_mixed_evidence_ignores_the_broken_reference`.

Правильность этого поведения — вопрос к Архитектору, а не решение разработчика. §7.3 определяет `final_confidence` как произведение и не говорит, что делать с неизвестным качеством части evidence; §7.3 проверка 1 при этом требует проверять принадлежность `fragment_ids` поданному множеству на стадии извлечения, а не в предикате. Дублировать эту проверку здесь значило бы реализовать больше, чем требует §14.3. Вопрос оформлен change request'ом.

## Альтернативы

| Вариант | Почему отвергнут |
|---|---|
| View, отфильтрованный по порогу | Порог оказался бы литералом `0.55` в DDL миграции. Оператор правит `.env`, порог меняется для §7.3 и не меняется для §14.1 и §16 — расхождение молчаливое, ровно то, что §14.3 запрещает |
| View без порога, порог в каждом запросе | Условие размазывается по трём потребителям. То же, что §14.3 запрещает, только иначе |
| Скалярная функция, вызываемая на строку | Вызов N раз на выборку. Set-returning форма этого лишена: вызов один на запрос, и планировщик встраивает тело — проверено отсутствием узла `Function Scan` в `EXPLAIN` |
| Хранить `final_confidence` столбцом | В §3 столбца нет, то есть это change request. И величина производная: `quality` пересчитывается, хранимая копия устаревала бы молча |
| Порог в таблице настроек в БД | §30.3 уже назначил местом конфигурацию. Вторая точка хранения разошлась бы с первой |

## Последствия

Проще: порог остаётся там, где его ждёт §30.3, и его смена проверяема — `test_threshold_comes_from_configuration` показывает, что состав обучаемых фактов меняется.

Сложнее: Alembic функции не отслеживает, поэтому `alembic check` расхождение этой функции **не поймает**. Сторожат её только тесты `test_teachable.py`, и это записано в докстроке миграции. Кроме того, «точка композиции одна» держится grep-проверкой `test_threshold_not_inlined_by_consumers`, а не дисциплиной.

Если решение окажется неверным: переход на view механический, но потребует решить, где живёт порог, — то есть вернёт исходный вопрос.
