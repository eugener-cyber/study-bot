# ADR-0004: Умолчания §3, которых в спецификации нет

**Дата:** 2026-10-06
**Статус:** accepted
**Затрагивает модули:** `core/db/models.py`, `alembic/versions/0001_schema.py`

## Контекст

§3 ТЗ описывает четырнадцать таблиц, но описывает их неравномерно. Часть объявлена подробно, с типами и `NOT NULL`; часть — в краткой форме вида `subjects(id, user_id FK, title, created_at)`, где нет ни типов, ни обязательности.

Это **пробелы, а не противоречия**: двух конфликтующих утверждений в ТЗ нет. По §40 разработчик не вправе разрешать противоречия, но пробел заполнить обязан — иначе схему не создать. Решения собраны здесь, а не выведены заново на каждой таблице: иначе одна и та же логика применялась бы четырнадцать раз и где-нибудь разошлась.

## Решение

**1. Тип первичного ключа — `BIGSERIAL` везде.** Решение Архитектора (Issue #2, «BIGSERIAL везде»). §3 указывает тип явно только у `users.id`. Причина: единообразие с единственной явно указанной таблицей плюс запас на рост — `fragments` и `facts` прибавляют по десятки тысяч строк на материал.

**2. `PRIMARY KEY` у двенадцати таблиц, где написано просто `id`.** Слова `PRIMARY KEY` или `PK` в §3 встречаются дважды: у `users.id` и у составного ключа `review_states`. У остальных первичность выводится из имени. Вывод бесспорный, но зафиксировать его нужно, потому что из него берётся число индексов под первичные ключи в контракте схемы: **четырнадцать**, а не тринадцать — составной ключ `review_states` тоже даёт один индекс.

**3. `FK` без пометки `NULL` читается как обязательный, `FK NULL` — как необязательный.** §3 помечает `NULL` у части внешних ключей: `materials.subject_id FK NULL`, `sessions.material_id FK NULL`, три ключа в `quality_reports`. Если бы необязательность была умолчанием для всех, эта пометка не несла бы смысла. Проверяется тестом `test_nullable_foreign_keys_are_those_marked_null`, который читает §3, а не повторяет список.

**4. `created_at` — `TIMESTAMPTZ`, nullable, без server default.** Исключение одно: `review_states.created_at`, где §3 прямо пишет `NOT NULL DEFAULT now()`. Дописывать default остальным значило бы реализовать больше, чем требует §3; значение проставляет приложение.

**5. Внешние ключи ставятся там и только там, где §3 пишет `FK`.** В `llm_calls` пометки нет ни у `user_id`, ни у `material_id` — ограничений там нет. Возможно, это пропуск спецификации; вопрос вынесен в ревью кода, а не решён самостоятельно.

## Альтернативы

| Вариант | Почему отвергнут |
|---|---|
| `INTEGER` для ключей, кроме `users` | Вдвое меньше места в индексах, но смена типа позже требует миграции с перезаписью таблицы. Решение Архитектора — `BIGSERIAL` |
| Считать все внешние ключи необязательными | Обессмысливает явные пометки `NULL` в §3 и допускает материал без владельца |
| Добавить `FK` в `llm_calls` по своей инициативе | Реализация больше, чем требует §3. По §40 это вопрос, а не решение разработчика |
| Выносить каждое умолчание отдельным change request | Пробел — не противоречие; поток CR на четырнадцать таблиц остановил бы работу, не добавив информации |

## Последствия

Проще: все отклонения от буквы §3 собраны в одном документе, и ревью проверяет список, а не ищет их по коду. Контракт схемы (`test_models.py`, `test_schema_contract.py`) читает §3 как источник, поэтому появление новой пометки в ТЗ не требует правки тестов.

Сложнее: четыре решения из пяти основаны на чтении краткой формы §3. Если чтение неверно, неверна схема — но неверно единообразно, и миграция правится в одном месте.

Если решение 5 окажется пропуском спецификации: добавление внешних ключей в `llm_calls` — отдельная миграция, данных в таблице к тому моменту не будет.
