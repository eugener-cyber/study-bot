# CLAUDE.md

Операционные инструкции. Читаются в начале каждой сессии вместе со `STATE.md`.

## Десять инвариантов (ТЗ §1.2)

1. **Evidence First.** Факт хранит `fragment_ids`, вопрос наследует evidence от факта. Цепочка `question → fact → fragment → locator → исходник` не рвётся. Модель никогда не называет страницу или таймкод — только `fragment_ids`, которые проверяются программно.
2. **Планируется знание, а не вопрос.** Состояние повторения — на `fact`; вопрос выбирается в момент выдачи.
3. **Ничто от LLM не попадает в БД без валидации.** Путь `LLM → schema → business → evidence → БД`. Прямой путь запрещён.
4. **Learning state не меняется без ответа пользователя.** Показ вопроса FSRS не трогает.
5. **Abandoned ≠ wrong.** Брошенная сессия не меняет FSRS и не растит `lapses`; меняются только счётчики презентации.
6. **Rejected-вопрос не занимает слот генерации.**
7. **Fact identity стабильна.** Перегенерация вопросов не создаёт новый `fact_id`.
8. **Старые callback никогда не меняют состояние.**
9. **Processing stage атомарна.** Стадия либо завершена и отражена в `completed_stages`, либо не считается завершённой.
10. **Внешние знания не являются evidence.** Не сказанное в источнике помечается `derived = true`.

## Предикат обучаемости (§14.3)

Факт обучаем, если: не `suspended`, не `derived`, `final_confidence >= MIN_FACT_CONFIDENCE`, `generation_status <> 'unavailable'` и существует валидный вопрос. Один предикат на три места: знаменатель coverage, фильтр планировщика, создание `review_states`.

**Реализация появится в WP-02** — одной SQL-функцией или view, не тремя похожими условиями в разных модулях.

## Конвенции

- **Бизнес-логика — в `core/`.** В хендлерах `bot/` только разбор апдейта, вызов сервиса и рендер.
- **Доступ к БД — через `core/services`,** сессия прокидывается middleware (появится в WP-02).
- **Миграция Alembic на каждое изменение схемы.** Ручной SQL в продакшене исключён.
- **`mypy --strict` на `core/`,** `ruff` и `black` на всём.
- **Структура репозитория — ТЗ §2.3.** Пакеты создаются по мере надобности, а не заранее: пустой каталог не помогает, а мешает линтеру и читателю.
- **Имя ветки:** `feature/wp-NN-описание`. Форма скилла `two-agent-development`; в Плане реализации §1.1 пример приведён без префикса — берётся форма скилла, номер пакета играет роль номера задачи.

## Персональные данные и секреты

Репозиторий **публичный**. `ALLOWED_USER_IDS` — реальные Telegram id, то есть персональные данные; `BOT_TOKEN`, `TELEGRAM_API_HASH` — секреты.

Реальные значения существуют **только в локальном `.env`**, который в `.gitignore`. В `.env.example`, `.env.ci`, тестах и документации — плейсхолдеры.

## Канонические документы

- **`docs/ТЗ.md`** — каноническая копия технического задания. Версия указана в заголовке файла. Копия на рабочем столе заказчика — рабочая, но при расхождении верна эта.
- **`docs/План_реализации.md`** — порядок работ и критерии «Готово, если».

## Изменение ТЗ запрещено

ТЗ §40: если реализация обнаруживает противоречие, разработчик **не выбирает вариант самостоятельно**. Порядок: зафиксировать как change request → вынести Архитектору → обновить спецификацию и соответствующий acceptance-тест → только потом писать код.

Заявленное в плане «допущение» права разрешить противоречие не даёт.

## Процесс разработки

Двухагентная схема — ТЗ §41 и скилл `two-agent-development`. Полная инструкция, чек-лист Проверяющего, **операционный список костылей** и шаблоны артефактов:

```
~/.claude/skills/two-agent-development/
    SKILL.md        роли, цикл, жёсткие правила
    checklist.md    чек-лист, включая раздел «Ревью Плана разработчика»
    crutches.md     12 паттернов, каждый — основание отклонить PR
    templates.md    План разработчика, шаблон PR, отчёт ревью, ADR
```

Коротко: Issue → План разработчика → **approve плана** → ветка → PR → ревью по чек-листу → merge. Без approve плана код не пишется.

Обязательный approve на PR снят как неисполнимый (ТЗ §41.4). **Вердикт Проверяющего публикуется комментарием в PR; merge без него — нарушение §41.2.**

## Команды харнесса (План §1.4)

```
make install   поставить окружение
make check     ruff + black --check + mypy --strict core/ + pytest
make lint      только линтеры
make type      только mypy
make test      только тесты
```

`make check` — ровно то, что выполняет CI: workflow вызывает эту цель, а не повторяет цепочку.

Остальные команды харнесса — `reset`, `seed`, `dump-material`, `session`, `answer`, `cite`, `evals` — появляются начиная с WP-02, когда будет что сбрасывать и чем заполнять.
